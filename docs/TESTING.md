# Atlas Testing and Evaluation Strategy

## Purpose

Atlas must verify conventional software behavior and probabilistic AI quality. Tests should arrive with each vertical slice, not after the platform is assembled.

## Test layers

- **Unit tests:** domain rules, state transitions, validation, budgets, retry decisions, and deterministic transformations.
- **Integration tests:** PostgreSQL/pgvector, Redis, Kafka, model/tool adapters, checkpoints, and migrations using realistic disposable dependencies.
- **Contract tests:** API schemas, events, tools, model-provider adapters, and compatibility between producers and consumers.
- **End-to-end tests:** submit, execute, retrieve, evaluate, fail, retry, resume, and complete representative research jobs.
- **AI evaluations:** golden tasks for citation support, evidence coverage, answer completeness, groundedness, tool selection, and policy compliance.
- **Resilience tests:** timeouts, duplicate events, unavailable dependencies, partial agent failure, poison messages, restart/recovery, and replay.
- **Performance tests:** API latency, concurrent jobs, worker throughput, queue lag, database behavior, and cost under controlled load.
- **Security tests:** authentication/authorization, secrets exposure, dependency/container/IaC scanning, prompt injection, unsafe tool use, and data leakage.
- **Infrastructure tests:** Terraform validation, policy checks, Kubernetes manifest/chart checks, deployment health, rollback, backup, and restore.

## Evaluation principles

- Begin with a small human-reviewed golden dataset before tuning prompts or agents.
- Version prompts, models, datasets, evaluators, and thresholds with results.
- Use deterministic assertions where possible and calibrated graders where judgment is necessary.
- Do not let a model grade itself as the only quality signal.
- Track quality together with latency, token usage, cost, and failure/recovery behavior.
- Review evaluator disagreements and prevent benchmark leakage.

## CI/CD quality gates

Pull requests should eventually run formatting/linting, type checks, unit tests, relevant integration and contract tests, migration checks, security scans, and fast AI regression tests. Main-branch or release workflows may run broader end-to-end, evaluation, container, infrastructure, and deployment verification.

Thresholds will be introduced from measured baselines. A failing required gate blocks promotion; production rollout must support health verification and rollback.

## Real Kafka producer and topic administration testing (Milestone 13 Slice 13C1)

- Network-free unit tests (`tests/outbox/test_kafka_producer_unit.py`) inject a fake `_RdKafkaProducerLike` double (via a private `_producer_factory` constructor seam) so no real socket, background thread, or broker connection is ever created. Kafka error classification is centralized in `atlas.outbox.kafka_errors.classify_kafka_error`, applied uniformly by `KafkaEventProducer` to delivery-callback errors, immediate `produce()` failures, and `flush()` failures, and follows a narrow, fail-closed policy (never stringified/exception-name matching): an unrecognized/non-`KafkaError` payload is fatal; `error.fatal()` is fatal; `error.retriable()` is recoverable (Confluent's documented operation-retry signal); `error.code() == KafkaError._MSG_TIMED_OUT` is recoverable as a single, narrow, real-client-evidenced exception specific to Atlas's durable outbox (librdkafka reports a per-message delivery timeout as `fatal=False, retriable=False` once its own internal retry budget is exhausted; this only proves Atlas did not receive broker-confirmed delivery within the configured deadline, not that the broker never received the record, and is treated as recoverable at the durable-outbox level consistent with Atlas's documented at-least-once contract — a later outbox-relay retry of the same event may duplicate the record on the topic, which is handled by the stable `event_id` plus the consumer inbox/deduplication implemented in Slice 13C2A, never by claiming exactly-once behavior); every other nonfatal, nonretriable error (e.g. `_BAD_MSG`) is fatal, per Confluent's own guidance that an error with neither classification set is non-retriable/permanent. No further codes are added to the `_MSG_TIMED_OUT` exception without a real integration test proving the exact code and documenting why retrying the durable event is safe. - **Slice 15C (advisory analyst):** tests assert the analyst's tool surface exposes no mutation capability (no restart/retry/config-change/deploy/alert-ack/DB-write/infra-API tool is ever registered), and that it produces a correct explanation for a sanitized, fixture-based test incident.
- **Milestone 16 (security/supply-chain CI):** a deliberately vulnerable test dependency/fixture must be caught by dependency scanning; a planted test secret must be caught by secret scanning; authenticated-endpoint tests cover unauthenticated/unauthorized structured rejection; CI workflow validation confirms actions remain pinned to full commit SHAs.
- **Milestone 17 (frontend + frontend container):** frontend lint/type-check/unit/component tests plus backend integration tests for the new document-upload endpoint; no `any` without a reviewed justification comment; CI additionally builds, starts, smoke-tests, and scans the new frontend image alongside the backend images already covered by Milestone 14.
- **Milestone 18 (local Kubernetes/Helm on `kind`):** CI Helm lint/template validation; CI `kind` deployment and smoke testing where practical; manual/CI-driven upgrade, rollback, and recreation drills.
- **Milestone 19 (full local E2E):** the same E2E/load/failure/backup-restore suite runs against both the Docker Compose stack and the `kind`/Helm stack; this is the local release gate.
- **Milestone 21 (Terraform):** `terraform fmt -check`, `terraform validate`, TFLint, and Checkov/tfsec run in CI; `terraform plan` runs on every PR; apply is a protected, reviewed action, never automatic.
- **Milestone 22 (EKS):** the same Helm charts and smoke tests proven on `kind` in Milestone 18 are re-run against the provisioned EKS cluster — EKS is not the first place they run.
- **Milestone 23 (cloud CI/CD):** the full required pipeline (tests → security/secret scans → image builds/scans/SBOMs → container smoke tests → `kind`/Helm tests → Terraform plan → staging deploy → post-deploy smoke/E2E → promotion → production deploy → health verification → rollback) is exercised, including a deliberately bad deploy proving rollback works.
- **Milestone 24 (final cloud validation):** cloud-environment load/failure/recovery/backup-restore drills mirror Milestone 19's local drills.
