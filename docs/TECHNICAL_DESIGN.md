# Atlas Technical Design

## Governing architecture rule: local-first, cloud-portable

Every cloud capability must first have a working local equivalent whenever technically practical. AWS hosts and operationalizes an already-validated system; AWS must not become the first environment where Atlas components are integrated.

- Application/domain behavior must not directly depend on AWS-specific APIs.
- The same application contracts and Docker images flow through local processes, Docker Compose, local Kubernetes (`kind`), and AWS EKS.
- Helm charts must be validated on `kind` (Milestone 18) before EKS (Milestone 22).
- PostgreSQL, Redis, Kafka, storage, ingress, secrets, telemetry, and workload boundaries each require an explicit local-to-AWS mapping (Milestone 20).
- AWS-only capabilities that cannot be reproduced faithfully — IAM, WAF, Route 53, managed-service failover, AWS networking — still require a local contract/configuration boundary where practical, automated configuration/contract tests, an explicit local-to-AWS mapping and trade-off analysis, and final integration validation in AWS.
- Do not claim full behavioral equivalence where local emulation is incomplete. This rule does not authorize working ahead of the milestone marked **Current** in `docs/LOCAL_BUILD_PLAN.md`.

## Status

Local foundation decisions are recorded as they are validated. The comprehensive local-to-AWS system architecture remains incomplete until working local components exist and the Visio diagrams are reviewed.

## Validated local decisions

### Application package and API entrypoint

- Python 3.12 is the only supported runtime (`requires-python = ">=3.12,<3.13"`), managed with `uv` and a committed lockfile.
- Application code lives under `src/atlas` and is installed as the `atlas` package.
- The FastAPI application entrypoint is `atlas.main:app`.
- `GET /health` is process liveness and does not open database connections.
- `GET /ready` lazily checks PostgreSQL connectivity; SQLAlchemy database errors return `503 {"status":"not_ready"}` without exposing credentials, while unexpected programming errors propagate.
- Quality gates are Ruff format, Ruff lint, mypy (strict, `src` and `tests`), and Pytest.
- Ruff owns formatting and import sorting; black and isort are not dependencies.
- Runtime dependencies (FastAPI, Uvicorn, SQLAlchemy, psycopg, Alembic, pydantic-settings, langgraph, langgraph-checkpoint-postgres, langchain-core, langchain-openai, langchain-anthropic) are separated from development dependencies (Pytest, httpx2, Ruff, mypy).

### Continuous integration

- One GitHub Actions workflow (`.github/workflows/ci.yml`) runs on pull requests and pushes to `main`.
- The workflow uses `permissions: contents: read` only.
- Actions are pinned to full commit SHAs (`actions/checkout`, `astral-sh/setup-uv`) with version comments.
- `setup-uv` is configured with `version: "0.11.8"`, `python-version: "3.12"`, and `enable-cache: true`.
- Dependencies install with `uv sync --frozen`.
- CI runs the same local gates: `ruff format --check .`, `ruff check .`, `mypy src tests`, and `pytest`.
- CI provides a Postgres 16 service and sets `ATLAS_DATABASE_URL` to the dedicated `atlas_test` database; Pytest owns empty-schema reset and Alembic upgrade.

### ResearchJob domain model

- Domain code lives under `atlas.domain` and depends only on the Python standard library.
- `ResearchJob` is a slotted entity with read-only properties; callers change lifecycle state through `start()`, `complete(result)`, and `fail(reason)`.
- Construction always creates `PENDING` jobs with stripped `id` and `question`; result and failure fields start empty.
- Allowed transitions are `PENDING → RUNNING → COMPLETED` and `PENDING → RUNNING → FAILED`.
- Terminal states (`COMPLETED`, `FAILED`) reject further lifecycle transitions.
- Optional timezone-aware timestamps make creation and transitions deterministic; omitted timestamps default to current UTC. Supplied timezone-aware timestamps are normalized to UTC.
- Timestamps must be timezone-aware and must not move earlier than the job's `updated_at`.
- Domain errors are `InvalidResearchJobError` for field/timestamp invariants and `InvalidTransitionError` for illegal status changes.
- Durable state is rebuilt with `ResearchJob.reconstitute(...)`, which validates status/field consistency without applying transitions.

### PostgreSQL persistence

- Local Postgres 16 runs via Docker Compose; host port `127.0.0.1:5433` maps to container `5432` (localhost-only publish); databases `atlas` (app) and `atlas_test` (tests). Compose credentials are development-only.
- Settings load `ATLAS_DATABASE_URL` through `pydantic-settings`; engines and sessions are created lazily.
- ORM model `research_jobs` uses `TIMESTAMPTZ` columns and CHECK constraints for status/field combinations as defense in depth.
- Nullable `idempotency_key` / `request_fingerprint` columns support API idempotency; a CHECK requires both null or both set; a unique constraint applies to non-null keys (PostgreSQL treats NULLs as distinct).
- `SqlAlchemyResearchJobRepository` implements the application `ResearchJobRepository` Protocol (`add` with required idempotency metadata, `get`, `get_by_idempotency_key` → `ResearchJobIdempotencyRecord`, `save`) with caller-owned `session_scope` transactions.
- Duplicate primary keys raise `ResearchJobAlreadyExistsError`; duplicate idempotency keys raise `IdempotencyKeyConflictError`; unrelated integrity failures are re-raised unchanged. `session_scope` performs rollback when exceptions escape.
- Job ids are capped at 128 characters in the domain (`MAX_RESEARCH_JOB_ID_LENGTH`), matching the persistence column.
- Status-specific timestamp orderings are enforced in domain reconstitution and mirrored by database CHECK constraints.
- Integration-test helpers live only under `tests/integration/`; they parse URLs with SQLAlchemy, require `atlas_test` or `*_test`, reset once per suite with AUTOCOMMIT `DROP SCHEMA public CASCADE` / `CREATE SCHEMA public`, run `alembic upgrade head`, initialize LangGraph checkpoint tables via `PostgresSaver.setup()`, and truncate Atlas job/audit/model-ledger rows plus checkpoint data between tests.

### Research-job HTTP API

- Versioned routes live under `/v1`; `/health` and `/ready` remain unversioned ops endpoints.
- `POST /v1/research-jobs` accepts a trimmed question (1–8000 chars) and required `Idempotency-Key` (max 128), creates a server-side UUID4 id via `ResearchJobService`, persists a `PENDING` job, and returns `202` with `ResearchJobResponse`.
- Matching idempotent replay returns the original job with `202`; key reuse with a different canonical payload returns structured `409`.
- `GET /v1/research-jobs/{job_id}` returns `200` or structured `404`.
- Request fingerprints hash deterministic canonical JSON of the normalized create request (currently `{"question": ...}` only).
- Structured `ErrorResponse` covers application errors and `RequestValidationError` (`422`). Only `sqlalchemy.exc.OperationalError` maps to research-job API `503`; other failures are not hidden as unavailable.
- Idempotency key values are not returned in bodies, error details, or logs.
- The application service is FastAPI-independent but coordinates SQLAlchemy `sessionmaker`/`session_scope` transactions; no Unit of Work abstraction.
- Verified on `main` through Pull Request #7 (pull-request CI and resulting `main` CI green).

### Background worker

- Separate process entrypoint: `python -m atlas.worker`.
- Claims use `SELECT … FOR UPDATE SKIP LOCKED` for `PENDING` or lease-expired `RUNNING` jobs; every claim/reclaim sets a new `secrets.token_hex(32)` token and `lease_expires_at`.
- `ClaimedResearchJob` carries the domain job plus claim token; lease/token columns are not on the domain entity or public API schemas.
- Domain `start()` / `complete()` / `fail()` remain authoritative; repository claim/finalize applies those transitions then persists.
- Fenced finalize requires matching job id, `RUNNING` status, and claim token in one transaction; clears token/lease atomically on success; returns `False` without modifying the row on ownership loss.
- `ResearchJobProcessor` is a Protocol: `(question: str, *, job_id: str) -> str`. The worker owns claim/finalize and does not import LangGraph.
- Defaults: poll 1s, processing timeout 60s, lease 90s (Milestone 8 locally validated defaults; may be tuned later); no heartbeat renewal.
- The 60-second worker processing timeout is orchestration-only (`Future.result(timeout=…)` on a single-thread executor). It does not cancel or interrupt the processor thread. Late results are ignored permanently and cannot finalize. New claims are refused while an abandoned processor still occupies the pool thread.
- Bounded shutdown: stop claiming, wait at most `shutdown_grace_seconds` (default equals the processing timeout), then `shutdown(wait=False)`. Python cannot kill processor threads and does not guarantee process exit if a callable remains blocked; operators may need SIGKILL. Hard termination of arbitrary LLM/tool/graph work requires process isolation or an external worker later. Milestone 8 does not add unsafe thread-based cancellation to claim a harder timeout.
- Processing is at-least-once: claim tokens fence stale database finalization but cannot undo duplicate in-process work.
- Verified on `main` through Pull Request #8 for the worker foundation, Pull Request #10 for the Milestone 7 LangGraph processor, and Pull Request #11 for Milestone 8 model providers.

### LangGraph research workflow

- Package `atlas.workflow` holds typed state, five nodes (`validate` → `plan` → `research` → `draft` → `complete`), sync `PostgresSaver` runtime, and `LangGraphResearchProcessor`.
- Plan and draft are model-backed through Atlas `ResearchPlanner` / `ResearchDrafter` Protocols. Research uses governed `ResearchPlanExecutor` tools and persists search hits as durable evidence. Graph state carries `findings: list[str]` plus `evidence_item_ids` and structured `claims` (Milestone 10A).
- Capabilities are injected via LangGraph typed runtime context: `WorkflowRuntimeContext` (renamed from `ModelRuntimeContext`), `StateGraph(..., context_schema=WorkflowRuntimeContext)`, `graph.invoke(..., context=...)`, and `Runtime[WorkflowRuntimeContext]` inside nodes. No module-level `ContextVar` for model/tool wiring.
- Stable LangGraph `thread_id` is the research `job_id`. Resume of unfinished work uses `graph.invoke(None, config, context=...)` and must not resend the original input. Runtime context is not checkpointed. Missing `evidence_item_ids` / `claims` on older checkpoints are treated as empty.
- Checkpoint tables are LangGraph-owned and created only through an explicit worker-startup `PostgresSaver.setup()` path (not per job). Atlas Alembic migration `20260809_0004` owns `workflow_executions` / `workflow_node_executions`; `20260809_0005` owns the model invocation ledger; `20260809_0006` owns the tool invocation ledger; `20260809_0007` owns evidence/provenance/report tables.
- Checkpoint writes, Atlas audit writes, ledger writes, and evidence writes use separate connections/transactions and are not atomic together; after a crash they may briefly disagree. Checkpoints are the resume source of truth; audit/ledger/evidence rows are operational history. Report artifact persistence is idempotent by `workflow_execution_id` so a commit-before-job-finalize window can safely retry.
- One `workflow_executions` row per worker processing attempt; attempts for a job share `thread_id`. Reclaim creates a new execution and marks prior `RUNNING` executions `ABANDONED` when practical. Node attempts are append-only with unique `(workflow_execution_id, node_name, attempt)`.
- Node wrappers and workflow-level processor handling catch `Exception` only so `KeyboardInterrupt` / `SystemExit` propagate; ordinary node failures mark audit rows failed. Persisted node errors are class-only (`<ExceptionClass>: node execution failed`) and never store raw exception messages.
- Graph nodes never call `finalize_*` or mutate `ResearchJob` lifecycle.
- Final result is a report with sections `Question`, `Plan`, `Findings`, `Draft`, and `Citations` when claims exist.

### Model providers and invocation ledger (Milestone 8)

- LangChain `BaseChatModel` is Atlas’s model boundary. `ChatOpenAI` and `ChatAnthropic` are instantiated only in the composition/configuration layer (`atlas.models.langchain` / `atlas.models.composition`). Workflow and domain code do not import provider SDKs.
- Default provider is `fake`. Deterministic fakes implement Atlas planner/drafter Protocols directly and do not require LangChain fake model classes. Real OpenAI/Anthropic calls require explicit provider selection and credentials.
- OpenAI uses langchain-openai with `use_responses_api=True` (verified against the pinned package). `ATLAS_MODEL_CALL_TIMEOUT_SECONDS` (default 25) is the provider HTTP/SDK request timeout and the ledger attempt `deadline_at` duration. Atlas does not enforce a separate hard wall-clock around the entire structured-invoke path (validation, ledger I/O, etc.).
- Provider exceptions are translated into Atlas-owned categories at the adapter boundary (`ModelTimeoutError`, `ModelRateLimitedError`, etc.). Provider-specific exception types must not leak into workflow, domain, API, or persistence code.
- Two-table invocation ledger: `model_invocations` (logical idempotent invocation + cached validated output) and `model_invocation_attempts` (every physical provider attempt with explicit `deadline_at`).
- Atlas prevents another provider call when a validated success is committed for the same invocation key. Atlas cannot guarantee exactly-once provider billing if the process dies after the provider completes a request but before the ledger commit.
- Concurrent calls with the same invocation key fail fast with `ModelInvocationInProgressError` (no wait/poll while holding a worker claim).
- A stale in-progress invocation may be reclaimed only after its attempt deadline has expired and the owning research-job claim is no longer valid.
- Attempt finalization is fenced with conditional SQL updates: a physical attempt may leave `STARTED` only while still `STARTED`, and the logical invocation is updated only when that attempt remains the latest active attempt for the invocation. A late result from a superseded attempt raises `ModelAttemptOwnershipLostError` and must not overwrite newer status, output, metadata, or error fields.
- Ledger captures provider, model, prompt version, token usage, latency, status, error class/retry class, and estimated cost. It never stores API keys, raw exception messages, complete prompts, or complete model responses.
- Estimated cost uses a versioned pricing catalog (`PRICING_VERSION`); values are labeled estimates; unknown models leave estimated cost null.
- Opt-in live OpenAI and Anthropic structured-plan verification passed locally (2026-08-09). Milestone 8 is Complete through Pull Request #11 (PR CI and resulting `main` CI green).

### Governed research tools and MCP (Milestone 9)

- Atlas-owned Pydantic contracts (`WebSearchInput`/`Output`, `FetchUrlInput`/`Output`) and a typed `ResearchTool` Protocol live under `atlas.tools`. Domain/application/workflow import only Atlas ports/contracts — never FastMCP, Tavily SDK, or raw httpx clients.
- `ToolRegistry` + `NodePermissionPolicy` allow `web_search`/`fetch_url` only on the research node (workflow) and on MCP origin; other workflow nodes have empty allowlists.
- Default `ATLAS_TOOL_PROVIDER=fake` uses deterministic fake search/fetch. Live search uses Tavily’s HTTP API via direct streaming `httpx` (`POST https://api.tavily.com/search`, Bearer auth) with required JSON content-type, optional `Content-Length` pre-rejection, and streamed byte caps before JSON deserialize.
- Live arbitrary-URL fetch is **unavailable** in Milestone 9. A concurrency-safe request-scoped transport that connects to a validated public IP while preserving TLS SNI/certificate verification was required; process-global `socket.getaddrinfo` monkeypatching is explicitly rejected as unsafe. Until such a transport or a controlled egress boundary exists, `ATLAS_TOOL_FETCH_ENABLED=true` fails at composition with `ToolAuthConfigError`. Under `tool_provider=tavily`, `fetch_url` is not registered (never substituted with fake fetch). HTML extraction (e.g. BeautifulSoup/lxml) and full SSRF-safe live fetch are deferred, not implemented. Fake fetch validates scheme/port/userinfo only.
- Research-node budgets (orchestration only, not thread kill): max 6 logical calls, max 2 attempts/call, 8s attempt timeout, 45s node deadline, remaining-budget checks before start/retry. Exhaustion raises `ToolBudgetExhaustedError` rather than returning incomplete findings as success.
- Projected findings are capped at 4 KiB and prefixed with `[untrusted_source]` before draft prompts; draft system prompts instruct that findings are untrusted external data, not instructions.
- Two-table tool ledger (`tool_invocations`, `tool_invocation_attempts`) mirrors model-ledger fencing. Logical identity includes job/node/tool/provider/input fingerprint/`tool_policy_version` (workflow) or origin+actor/tool/provider/input/`tool_policy_version` (MCP). Workflow execution id is physical attribution, not part of the logical key. Workflow rows also store `workflow_node_attempt` from the research-node audit hook.
- FastMCP stdio server (`python -m atlas.mcp`) delegates to the same `ToolInvocationService`. MCP stamps `origin=MCP` and a per-process UUID `actor_id` generated at server import/start — never accepted from tool arguments; workflow attribution fields are not MCP inputs; workflow FKs are NULL for MCP rows. Atlas `ToolError` failures are raised as FastMCP `ToolError` (sanitized; `mask_error_details=True`) so clients observe MCP errors rather than successful payloads containing error dicts. Production LangGraph research does not route through MCP.
- Default CI uses fake tools and makes no live network calls. Opt-in live tool tests require `ATLAS_ENABLE_LIVE_TOOL_TESTS=1` and credentials.

### Evidence and provenance (Milestone 10A)

- `atlas.evidence` owns ingest/normalize/chunk contracts, URL canonicalization, citation validation, and idempotent final report persistence. Persistence tables: `sources`, `documents`, `evidence_items`, `evidence_job_links`, `report_artifacts`, `claims`, `citations` (Alembic `20260809_0007`).
- Document identity is `UNIQUE(source_id, content_sha256, parser_version)`. Identical bytes at different sources remain distinct documents.
- Hash meanings: `documents.content_sha256` = SHA-256 of accepted raw UTF-8 bytes; `evidence_items.content_sha256` = SHA-256 of normalized item UTF-8 text; `report_artifacts.content_sha256` = SHA-256 of the canonical rendered report UTF-8.
- Citations require job linkage via `evidence_job_links`. Composite FK `(research_job_id, evidence_item_id)` prevents cross-job citation at the database; application validation fails closed first. Every persisted claim cites ≥1 linked evidence item; otherwise claims are empty and no unsupported claim rows are written.
- `ReportArtifactService.persist_final` is idempotent by `workflow_execution_id` (unique). Matching body hash + canonical citation mapping replays; mismatch raises `ReportArtifactConflictError`.
- HTTP: `POST /v1/evidence/documents` (UTF-8 text/Markdown JSON), `GET /v1/evidence/items/{id}`, `GET /v1/research-jobs/{id}/citations`.
- Drafter evidence packs enforce max 8 items, max 1,500 Unicode code points per item display text, and max 12,000 UTF-8 bytes across those display texts only (IDs/URIs/labels/prompt framing are outside the byte budget).
- Markdown normalization (`markdown.normalize.v1`) preserves structural whitespace (fenced/indented code, nested lists, tables, internal spaces); it is not plain-text whitespace collapsing. Normalized Markdown that contains only whitespace is rejected. IPv6 URL literals are rejected in Milestone 10A.

### Embeddings and semantic retrieval (Milestone 10B)

- Local Postgres uses `pgvector/pgvector:pg16` (Compose + CI). One database continues to hold relational and vector data.
- Alembic `20260809_0008` enables `vector`, creates `evidence_embeddings` with PK `(evidence_item_id, embedding_profile)`, FK to `evidence_items` `ON DELETE CASCADE`, fixed `vector(1536)`, `dimensions = 1536` check, and partial HNSW cosine index `ix_evidence_embeddings_hnsw_cosine` for `embedding_profile = 'embeddings.v1'` (keeps the profile-scoped ANN candidate query index-eligible).
- Profile `embeddings.v1`: OpenAI live model `text-embedding-3-small` at 1536 dimensions via LangChain only. Default provider is deterministic `fake` (stable digest-based token features; tests pipeline behavior, not real semantic quality). Optional `openai` requires credentials; composition constructs providers.
- Embedding identity is `(evidence_item_id, embedding_profile)`. New evidence is embedded after evidence commit; idempotent document replay does not duplicate embeddings; missing embeddings can be backfilled; existing rows are never overwritten silently. Provider calls run outside long DB transactions with bounded batch/item caps. Provider/config/timeout failures become typed `atlas.embeddings` errors. Partial failure: evidence can exist without an embedding when the provider fails after evidence persistence; backfill recovers.
- `EvidenceRetriever` embeds the query, then retrieves with cosine distance, deterministic `(distance, evidence_item_id)` ordering, `k` default 5 / hard max 8, optional source-kind / strength / job-link filters, and full evidence→document→source provenance on every hit.
  - **Exact mode** (offline CI metric gate): transaction-local `SET LOCAL enable_indexscan/bitmapscan = off` forces a non-approximate scan for deterministic cosine ranking. Settings are transaction-scoped and do not leak across pooled connections.
  - **HNSW mode** (production-oriented local default via `ATLAS_RETRIEVAL_USE_HNSW`): an inner candidate query orders solely by `embedding <=> query` with `LIMIT` (optionally over-fetching up to `HNSW_CANDIDATE_MULTIPLIER`, capped by `MAX_HNSW_CANDIDATES` when filters apply), then metadata filters run on candidates, then final deterministic `(distance, evidence_item_id)` ordering capped to `k`. This shape is eligible for `ix_evidence_embeddings_hnsw_cosine` and is verified by an EXPLAIN integration test under controlled test-only planner settings (`enable_seqscan = off`). PostgreSQL still owns normal production planner decisions; Atlas does **not** claim every production query is guaranteed to use HNSW. HNSW filtered retrieval uses a bounded over-fetch candidate pool, currently capped at 64. Highly selective metadata filters may return fewer than `k` results when matching evidence falls outside that approximate candidate pool. Exact mode remains available when deterministic exhaustive behavior is required.
- Typed embedding failures from document ingest map to the shared `ErrorResponse` envelope (`embedding_invalid_request`→422, `embedding_conflict`→409, auth/timeout/rate-limit/provider→503) with sanitized messages only. Evidence may already be committed before the embedding error (partial failure); replay/backfill does not duplicate rows.
- Implemented embedding profile is restricted to `Literal["embeddings.v1"]` in settings (plus adapter defense-in-depth).
- Research node: after search evidence persists, retrieve operator-corpus (and appropriate filters), link retrieved IDs to the job, merge/dedupe with search IDs preserving rank order, apply evidence-pack caps, draft, and validate citations. No invented citations when retrieval yields nothing usable. Checkpoints lacking Slice 10B fields remain backward-compatible (runtime context carries retriever; not checkpointed).
- Offline eval fixture + Recall@K / MRR@K gate (Recall@5 ≥ 0.80, MRR@5 ≥ 0.70) validates deterministic fake embeddings and **exact** cosine pipeline geometry — not real-world semantic quality. Opt-in live embedding checks use `ATLAS_ENABLE_LIVE_EMBEDDING_TESTS=1` and never run in default CI.

### Recovery, repair, and retry policy (Milestone 12 Slice 12B)

- Graph topology (Slice 12B): `validate → plan → research → draft → verify_citations → evaluate → policy → {complete | repair | await_review | terminal}`. `repair → draft` (re-enter draft only; never plan/research). `await_review → complete`. Compiled with `interrupt_after=["await_review"]` by default; passing policy → complete is NOT interrupted because `await_review` is not on that path (proven by spike).
- Recovery policy in `atlas.recovery.policy`: `decide_for_evaluation` routes based on hard/soft dimension failures and attempt caps (max repairs=1, max retries=2, max eval attempts=4). `decide_for_exception` categorizes transient vs permanent exceptions for retry/terminal. Exception categorization uses an `isinstance` registry with typed categories (TRANSIENT, PERMANENT, TERMINAL ownership/conflict) and string-name fallback for third-party exceptions only.
- Structure repair policy: `QUALITY_STRUCTURE` with `repair_count==0` triggers repair (`STRUCTURE_REPAIR`); `repair_count>=1` is terminal. `QUALITY_CITATION_INTEGRITY` and `QUALITY_TOOL_POLICY` are immediate terminal. Ownership/conflict exceptions (`ClaimOwnershipError`, evaluation ownership/conflict) are always terminal — never retried.
- Exponential backoff: `delay = min(max_backoff, base * 2^(attempt-1)) + bounded_jitter`. Settings: `retry_base_seconds` (5.0), `retry_max_backoff_seconds` (60.0), `retry_jitter_max_seconds` (0.0 for deterministic local/CI).
- Processor bind logic: REVIEW_COMPLETE resumes active execution with `thread_id=execution_id`, verifies checkpoint `next==("complete",)`, invokes complete only. Lease reclaim (`NONE` + active RUNNING) resumes that execution. Policy `JOB_RETRY` abandons unfinished and creates a new execution with `thread_id=execution_id`. Fresh NONE without a resumable active execution does the same.
- `ProcessingOutcome` variants: `CompletedProcessing` (worker finalizes COMPLETED), `PausedForReview` (processor transitioned to AWAITING_REVIEW; worker does not finalize), `RetryScheduled` (processor transitioned to delayed PENDING with JOB_RETRY; worker does not finalize), `TerminalFailed` (processor failed execution; worker finalizes FAILED).
- Operator review API: `POST /v1/research-jobs/{job_id}/review-decisions` with required `Idempotency-Key`. Returns 404 when `ATLAS_REVIEW_API_ENABLED=false` (default). Approve transitions AWAITING_REVIEW → delayed PENDING with REVIEW_COMPLETE mode and active execution binding. Reject transitions AWAITING_REVIEW → FAILED. Same key + same fingerprint replays with 202; different fingerprint returns 409.
- Claim-fenced report persistence: `ReportArtifactService.persist_final` requires `claim_token` and verifies the job is RUNNING with matching claim_token, valid lease (`lease_expires_at IS NOT NULL` and `lease_expires_at > now`), in the same transaction as the artifact insert. `EvidenceOwnershipError` on failure. Accepts explicit `at: datetime | None` for testability.
- `DispositionHint` expanded to include `repair`, `await_review`, `retry` in addition to `complete` and `terminal`. Evaluation runner disposition stays `complete`/`terminal`; policy engine writes graph state disposition. Policy decisions are persisted in `policy_decisions` table with `decision_fingerprint CHAR(64)` unique constraint `(research_job_id, decision_fingerprint)` for idempotent replay. Inserts use transaction-safe `INSERT … ON CONFLICT DO NOTHING RETURNING id` (never `session.rollback()` inside the caller TX); callers use the returned authoritative id. Identical replay reuses the row; same fingerprint with inconsistent fields raises `PolicyDecisionConflictError`. Fingerprint is SHA-256 of canonical JSON inputs (job_id, execution_id, eval_run_id, decision, category, reason, repair/retry/eval counts).
- Repository: `schedule_retry` increments `job_retry_count` by 1. `increment_repair_count` and `increment_evaluation_attempt_count` are claim-fenced with hard caps (1 and 4 respectively). All claim-fenced methods accept explicit `at: datetime` for lease-valid fencing.
- Claim ownership validation (`_owns_running_claim`): requires status==RUNNING, exact `claim_token` match, `lease_expires_at IS NOT NULL`, and `lease_expires_at > at` (strictly later). All claim-fenced repository mutations pass explicit `at`. Processor-owned workflow execution `complete`/`fail`/`abandon` use claim-aware methods that also require the job’s active execution binding and matching execution ownership in the same statement. Retry scheduling verifies the claim before abandoning an execution and transitioning the job in one transaction. Operator rejection fails the paused execution under the AWAITING_REVIEW job lock (no worker claim).
- Fail-closed mutations: processor raises `ClaimOwnershipError` (sanitized, no tokens) on `False` from any claim-fenced mutation. Worker catches `ClaimOwnershipError` and calls `finalize_failure` which becomes a safe no-op when the claim is already lost. Processor never returns `PausedForReview`, `RetryScheduled`, or `CompletedProcessing` after ownership loss.
- Evaluation attempt accounting: job-global `evaluation_attempt_count` increments in the same transaction as a **new** `evaluation_runs` insert only (`EvaluationService.begin_or_resume`). Reclaim/replay of an existing attempt does not increment. Cap of 4 is claim-fenced; exceeding raises `EvaluationAttemptCapError`. Crash before commit rolls back both.
- Lease reclaim resumes the same active RUNNING execution when safe. Policy job retry creates a new workflow execution and checkpoint thread — do not conflate these behaviors.
- Structure failures: first `report_structure` failure with `repair_count=0` → repair; after one repair → terminal. Citation-integrity and tool-policy remain immediately terminal.
- Continuation modes: scheduling persists `JOB_RETRY` / review approval persists `REVIEW_COMPLETE`; `claim_next` copies pending mode into durable `claimed_continuation_mode`, clears pending mode, and returns the consumed mode on `ClaimedResearchJob`. Lease reclaim reads `claimed_continuation_mode`. `ContinuationMode` is a `StrEnum` (values: NONE, JOB_RETRY, REVIEW_COMPLETE).
- Composite FK `(active_workflow_execution_id, id) → workflow_executions(id, research_job_id)` with `ON DELETE NO ACTION`; pointer cleared on terminal transitions.
- Complete node authorization: passing evaluation **or** durable human-review approve override matching `fingerprint_grading_snapshot` for that exact execution/candidate. Disposition `await_review` alone never authorizes persistence.
- Worker orchestration timeout (`FuturesTimeoutError`) remains terminal for this milestone (no auto-retry while the processor thread may still run).
- Alembic head `20260809_0010` (0009 unchanged).

These decisions cover the verified foundation through Milestone 11 Complete on `main` (`c5d4749`), Milestone 12 Slices 12A and 12B merged to `main` through Pull Request #17 (`e3412c3`), and the local, not-yet-merged Milestone 12 human calibration closeout. They do not imply production semantic retrieval quality, messaging, or cloud topology choices.

### Specialist agents (Milestone 11)

### Transactional outbox and domain events (Milestone 13 Slice 13B)

- Package `atlas.eventing` owns frozen Pydantic envelopes for `research_job.created|completed|failed|awaiting_review|retry_scheduled` (event version 1 only), canonical deterministic JSON serialization, and the reserved topic name `atlas.research-job-events.v1`. Payloads never include secrets, raw exception text, claim tokens, idempotency keys, prompts, or evidence/report bodies.
- Table `outbox_events` (Alembic `20260809_0011`) stores durable unpublished events. `outbox_position` (identity) is the **global** authoritative relay publication order across the reserved topic `atlas.research-job-events.v1` (not per-aggregate); sequence gaps after rollback are expected and valid.
- Typed `OutboxRepository` inserts envelopes from application/processor/worker transactions. `claim_batch` treats the earliest unpublished row as a head-of-line barrier: if that row is locked by another transaction or holds an unexpired publish lease, the batch is empty and later positions must not be claimed. When the head is claimable, it claims a bounded contiguous run of eligible unpublished rows in ascending `outbox_position` using `FOR UPDATE SKIP LOCKED` on each specific row (never `WHERE claimable … ORDER BY` leapfrogging). Conditional mark/release require matching claim token + unexpired lease + `published_at IS NULL`. Explicit injected `at` timestamps fence all predicates. ``publish_attempts`` counts **claim attempts** (incremented when a row is claimed for publication), not producer I/O calls.
- Events are enqueued in the same caller-owned PostgreSQL transaction as the authoritative mutation (submit created; claim-fenced completion/failure; newly authoritative awaiting-review / retry-scheduled policy transitions). Idempotent job replay and policy replay must not duplicate events. Outbox failure rolls back the mutation; worker finalization must not recurse into failure handling or falsely report a terminal job.
- `OutboxRelay` acquires a singleton PostgreSQL advisory lock on a dedicated connection, claims a bounded batch, publishes through a typed `EventProducer` **outside** database transactions, then conditionally marks or releases using a **fresh** clock reading taken after each producer call so a slow publish cannot finalize an expired lease. Within a claimed batch, publication is strict by ascending `outbox_position`: a producer failure or lost mark ownership stops later rows (they are not published; owned claims are released when the lease still allows, otherwise left reclaimable after expiry). A crashed relay that leaves unexpired claims blocks replacement relays from leapfrogging until those leases expire. Delivery is **at-least-once**. A crash after producer acknowledgment but before `mark_published` republishes the same `event_id` after lease expiry; consumer inbox deduplication (Slice 13C2A) makes this safe by detecting the duplicate `event_id` before repeating any business effect. Multi-relay sharding is deferred. `run_once()` returns a typed `RelayBatchResult`/`RelayRunOutcome` (`EMPTY | PUBLISHED | RECOVERABLE_FAILURE | FATAL_FAILURE | OWNERSHIP_LOST | UNEXPECTED_FAILURE`) so a caller can distinguish an empty queue from a recoverable delivery failure, a fatal or unexpected producer failure, or lost lease ownership.
- Do not claim exactly-once delivery.

### Real Kafka broker and producer (Milestone 13 Slice 13C1)

- Broker: pinned `apache/kafka:4.3.1` (no floating tags) in single-node KRaft mode (combined broker+controller, no ZooKeeper). Docker Compose publishes only `127.0.0.1:9094` externally; the internal `PLAINTEXT://kafka:9092` listener serves other Compose containers (e.g. the one-shot topic-init service). GitHub Actions runs the same pinned image as a service container on port 9092, sized for the runner (single advertised `localhost:9092` listener, no persistent volume). Both use a static, non-secret development KRaft `CLUSTER_ID` and `auto.create.topics.enable=false`; both use a CLI-based health check (`kafka-broker-api-versions.sh`) with no arbitrary sleep.
- Topic administration is a typed `AdminClient` helper (`atlas.outbox.topic_admin`) that only ever operates on the fixed constant `RESEARCH_JOB_EVENTS_TOPIC_V1` (`atlas.research-job-events.v1`) — it never accepts an arbitrary runtime topic name. `ensure_topic_exists` idempotently creates the topic with exactly one partition (matching Slice 13B's global `outbox_position` ordering guarantee — Kafka ordering is partition-scoped, so v1 intentionally uses a single partition as a documented trade-off). `verify_broker_connectivity` and `verify_topic_partitioning` fail closed with a bounded timeout on an unreachable broker, a missing topic, or an existing topic with the wrong partition count; nothing relies on broker auto-topic creation. Local Compose runs this helper as a one-shot `kafka-topic-init` service (`python -m atlas.outbox.topic_admin`, using the shared backend image built in Milestone 14), gated on Kafka's health check and safe to rerun; CI runs the same Python `AdminClient` helper directly after `uv sync --frozen`.
- `atlas.outbox.kafka_producer.KafkaEventProducer` implements the `EventProducer` Protocol using `confluent-kafka` (`>=2.15.0,<3`, resolved `2.15.0`). For every event: topic is the fixed reserved-topic constant; key is `event_id` UTF-8 encoded; value is the existing canonical domain-event JSON UTF-8 encoded; headers are exactly `event_type`, `event_version`, `aggregate_type` (safe, non-secret values only). Configuration hardcodes `acks=all`, `enable.idempotence=true`, and `max.in.flight.requests.per.connection=5` (idempotence-compatible ordering) — these are not settings-configurable. `delivery.timeout.ms`, `socket.timeout.ms`, and `request.timeout.ms` are all bounded from `Settings`.
- A `publish()` call registers an explicit delivery callback and is successful only when **all three** hold: the callback was invoked; the callback reported `err is None`; and the subsequent `flush()` call returned zero outstanding messages. `atlas.outbox.kafka_errors.classify_kafka_error` is the single centralized helper `KafkaEventProducer` uses for every Kafka error it can observe (delivery-callback error, immediate `produce()` exception, or `flush()` exception). It applies a narrow, fail-closed policy, in order: (1) an unrecognized/non-`KafkaError` payload (e.g. a `KafkaException` with no identifiable `KafkaError` argument) is fatal — there is no signal to classify by; (2) `error.fatal()` is fatal; (3) `error.retriable()` is recoverable — this is Confluent's own documented operation-retry signal; (4) `error.code() == KafkaError._MSG_TIMED_OUT` is recoverable as a single, narrow, real-client-evidenced exception specific to Atlas's durable outbox: librdkafka reports a per-message delivery timeout as `fatal=False, retriable=False` once its own internal `delivery.timeout.ms` budget is exhausted. This error only proves that Atlas did not receive broker-confirmed delivery within the configured deadline — it does not prove the broker never received the record. Atlas treats it as recoverable at the durable-outbox level anyway, consistent with Atlas's documented at-least-once delivery contract: a later outbox-relay retry of the same `event_id` is permitted even though `retriable()` reports `False`, and any resulting duplicate on the topic (never claimed to be ruled out, and never an exactly-once guarantee) is handled by the stable `event_id` plus the consumer inbox/deduplication implemented in Slice 13C2A, not by this producer adapter; (5) every other error that is neither fatal nor retriable (e.g. `_BAD_MSG`, a malformed record) is fatal, per Confluent's guidance that an error with neither classification set is non-retriable/permanent. No further codes are added to step 4 without a real integration test proving the exact code and documenting why retrying the durable event is safe — this is not a general "assume nonfatal is recoverable" rule. A `BufferError` on `produce()` and a step-3/step-4 `KafkaError`/`KafkaException` raise a recoverable `KafkaPublishError` (or `KafkaPublishTimeoutError` for the missing-callback / nonzero-`flush()` cases); a step-1/step-2/step-5 error raises `KafkaFatalProducerError` and permanently marks the producer instance closed so it can never be reused. No exception raised by this adapter ever includes raw librdkafka message/error text, broker addresses, or configuration/environment values — every message is a fixed, sanitized class-name-style string.
- `OutboxRelay.run_once()` classifies a producer exception three ways (never a log string or exception name): `isinstance(exc, FatalEventPublishError)` → `RelayRunOutcome.FATAL_FAILURE`; `isinstance(exc, EventPublishError)` → `RelayRunOutcome.RECOVERABLE_FAILURE`; anything else (a programming error or other untyped exception) → `RelayRunOutcome.UNEXPECTED_FAILURE`, never assumed safe to retry. The row's claim is released the same way in all three cases, but only `FATAL_FAILURE`/`UNEXPECTED_FAILURE` tell the caller to stop and terminate.
- The executable `python -m atlas.outbox` is a Kafka-only runtime composition — it never constructs `FakeEventProducer` (which remains test-only via direct dependency injection into `OutboxRelay`; there is no settings-driven fake/real producer switch). Startup order is: load/validate `Settings`; construct PostgreSQL session/engine dependencies; construct `KafkaEventProducer`; acquire the singleton PostgreSQL advisory lock; verify Kafka broker connectivity; verify the fixed topic's partitioning; enter the poll loop. The relay is always constructed with `batch_size=1` (publication stays sequential, bounded by `kafka_delivery_timeout_seconds`). SIGINT/SIGTERM stop new claims but let the current timeout-bounded record finish; shutdown always attempts both a bounded producer close and advisory-lock release, in that order, regardless of whether the first step failed, before restoring the previous signal handlers. `EMPTY` / `RECOVERABLE_FAILURE` / `OWNERSHIP_LOST` outcomes back off for `outbox_relay_poll_interval_seconds` before the next claim; a `FATAL_FAILURE` or `UNEXPECTED_FAILURE` outcome, any unexpected PostgreSQL/session/advisory-lock exception, or a cleanup-step failure terminates the process nonzero without ever consulting `lock.held` to decide whether it is safe to keep running. There is no HTTP server in this executable.
- `Settings` adds `kafka_bootstrap_servers`, `kafka_delivery_timeout_seconds` (default 10s), `kafka_socket_timeout_seconds` (default 10s), `kafka_topic_verify_timeout_seconds` (default 10s), `kafka_delivery_timeout_lease_margin_seconds` (default 5s), and `outbox_relay_poll_interval_seconds` (default 1s). A model validator enforces `kafka_delivery_timeout_seconds + kafka_delivery_timeout_lease_margin_seconds <= outbox_publish_lease_seconds` (10 + 5 <= 30 by default) at construction time, raising with a sanitized message on violation — a claimed row can never outlive its lease while its Kafka delivery is still "in flight." There is no lease-renewal mechanism in this slice; larger Kafka batches remain deferred.

### Business Kafka consumer, inbox, and lifecycle projection (Milestone 13 Slice 13C2A)

- Package `atlas.consumer` owns consumer identity, strict decode/validation, the production `confluent-kafka` `Consumer` adapter, poll-decode-apply-commit orchestration, and typed application ports (`InboxRepository`, `ProjectionPort`). `identity.py` fixes the sole consumer group/client id as constants (`RESEARCH_JOB_PROJECTION_CONSUMER_GROUP_V1` = `atlas.research-job-projection.v1`, mapped 1:1 to `RESEARCH_JOB_PROJECTION_CLIENT_ID_V1` via `CLIENT_ID_BY_CONSUMER_GROUP_ID`) checked against an `ALLOWED_CONSUMER_GROUP_IDS` allowlist at construction — mirroring how `RESEARCH_JOB_EVENTS_TOPIC_V1` is a fixed, non-runtime-selectable topic constant; there is no settings-driven or caller-supplied way to select a different group. `KafkaEventConsumer` has no public `client_id` constructor parameter at all (it has no legitimate production variability independent of the already-fixed group id): the adapter looks up the client id internally from the validated `group_id`.
- `atlas.consumer.kafka_consumer.KafkaEventConsumer` hardcodes `enable.auto.commit=false` and `auto.offset.reset=earliest` (a brand-new consumer group must never silently skip the topic's history on first subscribe); `session.timeout.ms`/`max.poll.interval.ms` are bounded from `Settings` (`consumer_session_timeout_seconds` default 10s, `consumer_max_poll_interval_seconds` default 300s). It always subscribes to the fixed reserved topic; if `subscribe()` fails after the underlying librdkafka consumer was already constructed, the adapter attempts to close that consumer (best-effort; a close failure there is swallowed and never masks the original `SubscribeFailed` classification) before raising, so a partially-constructed consumer is never leaked. `commit_message()` treats a raised `KafkaException` and a *returned-but-unconfirmed* synchronous commit identically as failure: Confluent's own API documents that a non-raising `commit(asynchronous=False)` call still requires checking each returned `TopicPartition`'s error field, so `None`, an empty result, a non-list result, or any returned partition with a non-`None` error all raise `ConsumerError("CommitFailed")` — a raised exception is not the only failure signal this checks. Unlike `OutboxRelay`, no PostgreSQL advisory lock is acquired for the consumer: Kafka's own consumer-group protocol already guarantees at most one process actively owns the topic's single partition at a time.
- `atlas.consumer.deserialize.decode_message` strictly decodes and validates one Kafka record before it reaches any business logic: headers must be exactly `event_type`, `event_version`, `aggregate_type` (no missing/duplicate/undecodable/unexpected keys); the value must decode as UTF-8 JSON, be a JSON object, be no larger than 32 KiB (twice the outbox producer's 16 KiB payload cap plus envelope overhead — defense in depth, not a tight production bound), and pass the typed research-job event catalog's own `parse_domain_event` validation; and the header values must agree with the decoded envelope's own `event_type`/`event_version`/`aggregate_type`. Any failure raises a typed, sanitized `MalformedEnvelopeError` or `InvalidHeaderError` — never embedding raw header/value bytes in the exception message.
- `consumer_inbox` (Alembic `20260809_0012`) has composite primary key `(consumer_id, event_id)` and is the durable deduplication boundary for exactly one consumer identity. `atlas.persistence.repositories.consumer_inbox.SqlAlchemyInboxRepository.record_and_apply` checks for a prior `(consumer_id, event_id)` row first (safe under Kafka's single-active-reader guarantee for a one-partition topic), invokes the business effect only when absent, and inserts the inbox row in the same `session.flush()` — both commit together or neither does. A duplicate delivery skips the effect entirely but the Kafka record is still eligible for offset commit. A concurrent duplicate insert (e.g. a brief rebalance overlap) raises `ConsumerInboxConflictError` via the primary key's own `IntegrityError`, rather than being silently mistaken for an ordinary duplicate.
- `research_job_event_projection` (also `20260809_0012`) is the first business consumer: a durable, non-authoritative last-known-lifecycle read model keyed by `research_job_id`, built entirely from the reserved Kafka topic (never by reading `research_jobs` directly). `atlas.persistence.repositories.research_job_projection.SqlAlchemyResearchJobProjectionRepository.apply` upserts `last_event_id`/`last_event_type`/`last_event_at`/`updated_at`. Once a projection row records a terminal event (`research_job.completed` or `research_job.failed`), the domain guarantees no further event for that job is ever produced; because the inbox's `(consumer_id, event_id)` check always runs first, any event that still reaches `apply()` for an already-terminal row is necessarily a *different* event — an ordering-invariant violation the projection fails closed on via `LifecycleOrderViolationError` rather than silently overwriting the recorded terminal state. An exact redelivery of the same `event_id` never reaches this check.
- `atlas.consumer.runner.ConsumerRunner.run_once()` orchestrates one poll → decode → (PostgreSQL transaction: inbox record + business effect) → commit-offset cycle. The Kafka offset is committed synchronously, once, only after `session_scope` has returned normally — any exception raised before that point (decode failure, lifecycle violation, database error) propagates with the offset never committed, so the record redelivers on restart.
- The executable `python -m atlas.consumer` has no HTTP surface (matches `python -m atlas.outbox`'s existing precedent: its own process exit code is the health signal for its process supervisor). Startup order is: load/validate `Settings` and construct PostgreSQL session/engine dependencies; construct `KafkaEventConsumer` (subscribes to the fixed topic under the fixed group); install SIGINT/SIGTERM handlers; verify Kafka broker connectivity then the fixed topic's partitioning (reusing `atlas.outbox.topic_admin`); enter the poll loop. Every one of these startup steps is wrapped so a failure yields a sanitized, class-name-only log line and a controlled nonzero exit rather than an uncaught traceback (a raw settings-validation error, for example, can otherwise embed the invalid environment-derived value in its own exception message). A settings/database-dependency failure never attempts consumer cleanup (no consumer exists yet); a Kafka-consumer-construction failure never attempts cleanup either (construction either fully failed, with nothing to clean up, or fully succeeded); a failure installing the signal handlers *does* close the already-constructed consumer before exiting, since the consumer exists by that point. Signal-handler installation itself (`_install_signal_handlers`) is not treated as atomic: SIGINT and SIGTERM are installed one at a time, and each successfully installed signal's previous handler is recorded as it succeeds, so if installing a later signal fails, `_restore_signal_handlers` puts back every signal already replaced (independently, best-effort, never letting one restoration failure skip the other) before the consumer is closed and the process exits 1 — the original "failed to install" classification is always the logged reason, regardless of whether the subsequent consumer close also fails. Every poll is bounded by `consumer_poll_timeout_seconds` (default 1.0s) so SIGINT/SIGTERM are observed between polls even when no records arrive. As of Slice 13C2B (see below), a decode/validation failure or a lifecycle-order violation is durably dead-lettered rather than terminating the process, a transient PostgreSQL error receives bounded in-process retry, and every other error (fatal database error, unexpected Kafka error, internal inbox conflict, or unexpected exception) still terminates the process nonzero with no retry and no offset commit. Normal shutdown's `_cleanup` always attempts to close the consumer (triggering a clean consumer-group leave) and always attempts to restore each previously-installed signal handler independently, regardless of whether the consumer close or an earlier restoration failed; `_cleanup` returns failure (forcing a nonzero exit) if any of these steps failed, and no such failure can escape `main()` as an uncaught traceback.
- Every log call in `atlas.consumer` uses only a fixed, sanitized message and, where useful, `exc.__class__.__name__` — never `str(exc)`, `repr(exc)`, `exc.args`, `exc_info`, or any secret, database URL, or Kafka broker address; no log line interpolates a settings-derived configuration value.

### Consumer retry, poison-event dead-lettering, and operator replay (Milestone 13 Slice 13C2B)

- Scope boundary: only the PostgreSQL-side "process one already-in-hand record" work is retried — the normal apply transaction, and (on a permanent-poison classification) the dead-letter upsert. `poll()` is never called again during a record's retry episode; the whole episode is bounded well inside `consumer_max_poll_interval_seconds` by a runtime processing deadline, not by Kafka's own liveness enforcement. A structured, evidence-backed transient `commit_message()` failure receives the same bounded attempts, shutdown-aware backoff, and processing-deadline enforcement as transient database work; a fatal or unrecognized commit failure terminates immediately. If bounded transient commit retries exhaust, processing terminates with the offset uncommitted. After a DLQ row was durably persisted, an ultimately unsuccessful offset commit surfaces as `OffsetCommitFailedAfterDeadLetterError` — redelivery after restart safely reuses that durable DLQ row rather than losing the record. No Kafka polling occurs during commit retry.
- Retry timing (`atlas.consumer.timing`): `worst_case_attempt_seconds = db_pool_timeout + db_connect_timeout + max_db_round_trips_per_attempt * db_statement_timeout + processing_overhead`; `worst_case_total_processing_seconds = max_attempts * worst_case_attempt_seconds + deterministic_exponential_backoff_sum + safety_margin`. `Settings` rejects construction unless `worst_case_total_processing_seconds < consumer_max_poll_interval_seconds`. Approved defaults (`consumer_retry_max_attempts=3`, `consumer_retry_base_seconds=1.0`, `consumer_retry_max_backoff_seconds=30.0`, `consumer_retry_jitter_max_seconds=0.0`, `consumer_retry_safety_margin_seconds=60.0`, `consumer_db_connect_timeout_seconds=5.0`, `consumer_db_pool_timeout_seconds=5.0`, `consumer_db_statement_timeout_seconds=5.0`, `consumer_retry_processing_overhead_seconds=2.0`, `consumer_max_db_round_trips_per_attempt=8`, `consumer_replay_lease_seconds=90.0`) compute to 52 seconds per attempt and 219 seconds total, comfortably under the 300-second `consumer_max_poll_interval_seconds`. `ProcessingDeadline` (message-received-at minus the safety margin) is checked before every attempt (`can_start_attempt`) and before every backoff sleep (`can_afford_backoff`, which requires the backoff plus one full conservative attempt bound); either check failing raises `ProcessingDeadlineExceededError` with the offset left uncommitted. Backoff is deterministic exponential (`base * 2^attempt_index`, capped at `max_backoff_seconds`) with jitter fixed at `0.0` by approved decision. The three `consumer_db_*_timeout_seconds` values this formula assumes are actually enforced only because `atlas.consumer.db.build_consumer_engine` — a dedicated, non-cached engine constructor used solely by `python -m atlas.consumer` and `python -m atlas.consumer.replay` — applies them to a real engine (libpq `connect_timeout`, SQLAlchemy `pool_timeout`, and PostgreSQL server-side `statement_timeout` via connection `options`); the shared, process-wide cached `atlas.persistence.db.get_engine` singleton used elsewhere in the application applies none of them and is never used by either consumer/replay executable. `build_consumer_engine` converts the configured connect-timeout seconds and statement-timeout milliseconds using ceiling rounding with a floor of 1 (`atlas.config.timeout_math.effective_connect_timeout_seconds`/`effective_statement_timeout_ms`), never Python's banker's-rounding `round()`: a naive `round()` can turn a small positive configured value into `0`, which libpq/PostgreSQL both treat as "no timeout" — the opposite of what a positive setting requests. This same effective (ceiling-rounded) conversion feeds both the `atlas.consumer.timing.worst_case_attempt_seconds` formula and `Settings._validate_consumer_retry_timing_margin`'s duplicated copy of it, so the static timing-margin proof always uses a value at least as large as what the real engine enforces at runtime — never a smaller, optimistic raw-float value that a fractional configured timeout could round up past. Backoff waits (both apply/DLQ-retry and Kafka-commit-retry, see below) are performed through an injectable `Waiter` (`atlas.consumer.wait.build_shutdown_aware_waiter`) that sleeps in small slices and checks the process's existing shutdown predicate between slices — never polling Kafka during backoff — so a shutdown signal observed mid-backoff raises `ConsumerShutdownRequestedError` and the poll loop exits cleanly within one slice interval, with the offset left uncommitted.
- Error classification (`atlas.consumer.errors`, `atlas.consumer.db_classify`, `atlas.outbox.kafka_errors`) is by exact exception type or structured `KafkaError` metadata only — never exception text or class-name strings. `PoisonEventError` subclasses (malformed envelope, invalid/missing/mismatched headers, oversized/undecodable value, invalid JSON/schema/catalog, and `LifecycleOrderViolationError`) each carry a fixed `ClassVar[str] failure_code` from an exact-type allowlist (`_FAILURE_CODE_BY_EXACT_TYPE` / `ALLOWED_FAILURE_CODES`); an unmapped `PoisonEventError` subclass fails closed via `UnmappedPoisonEventTypeError` rather than silently inheriting a parent's code. `classify_database_error` treats a SQLAlchemy `DBAPIError` as transient only when `connection_invalidated` is set or the underlying SQLSTATE is class `08`, `40001`, or `40P01`; every other SQLSTATE, a missing SQLSTATE, and every `IntegrityError` (even with a transient-looking SQLSTATE, since a constraint violation is never resolved by retrying the identical statement) classify as fatal. `KafkaEventConsumer` applies `atlas.outbox.kafka_errors.classify_kafka_error` (the same centralized helper `KafkaEventProducer` uses) to every `poll()` exception, `poll()`-returned broker-error message, and synchronous `commit_message()` failure (raised, or returned-but-unconfirmed): only an evidence-backed recoverable `KafkaError` raises `TransientKafkaError`, everything else (fatal, neither-flag-set, or an unrecognized/non-`KafkaError` payload) raises the fatal `ConsumerError`. A `commit_message()`-site `TransientKafkaError` is retried with the same bounded attempts/backoff/deadline machinery as a transient database error; a `poll()`-site one (raised before any record is in hand, outside any retry episode) is instead handled by `python -m atlas.consumer`'s own poll loop, which backs off and polls again rather than terminating the process. These are two deliberately different recovery horizons: per-record processing/commit retry is bounded (fixed attempts, exponential backoff, a runtime deadline); `poll()`-site broker-reconnect recovery is process-lifetime — it may continue indefinitely across separate polling cycles until the broker recovers or shutdown is requested, and never itself terminates the process. No Kafka polling ever occurs while an in-hand record is backing off (`poll()` is called exactly once, at the top of `run_once()`, before any retry loop begins), and a fatal/unrecognized Kafka error still terminates immediately at either horizon. Because a prolonged outage can otherwise log a fresh warning on every polling cycle, the poll loop's `_OutageWarningTracker` (thread-safe) logs at most one sanitized warning per outage episode, resetting as soon as any subsequent `run_once()` call returns without raising (a successful poll, whether or not it returned a message) so a later, separate outage still produces its own new warning. Transient infrastructure receives bounded retry then terminates with no offset commit and no DLQ row; DLQ-persistence failure retries only when transient, and exhaustion also terminates without an offset commit; every fatal/unrecognized error (`ConsumerInboxConflictError`, an unknown `IntegrityError`, a fatal/unrecognized Kafka error, a configuration error, or any unexpected exception) terminates immediately with no retry, no DLQ, and no offset commit.
- DLQ payload retention (`atlas.consumer.retention.build_retention`) is two-tiered: Tier A (`replay_eligible=true`) applies only to `lifecycle_order_violation` — the sole failure code reached only after the event already fully decoded and validated — and stores a bounded canonical reserialization plus the three validated fixed headers, nothing else. Tier B (`replay_eligible=false`, every other failure code, including an oversized value) stores only the complete SHA-256 hash and original byte length of the raw Kafka value — never the raw bytes, and never arbitrary header contents — so oversized or otherwise untrusted poison is still durably DLQ-able without retaining anything an attacker or a corrupt producer controlled. The retained canonical value's own size bound (`MAX_RETAINED_CANONICAL_VALUE_BYTES`) is numerically reconciled to equal `MAX_MESSAGE_VALUE_BYTES` (32 KiB, the maximum raw Kafka record value `atlas.consumer.deserialize` will decode at all) — a maximal-size raw value's *re-serialized* canonical form is not guaranteed to be smaller, so if it would still exceed the bound, retention degrades that record to Tier B (no canonical value or headers retained, `replay_eligible=false`) rather than raising or truncating.
- Migration `20260809_0013` adds `consumer_dead_letters` (uniqueness boundary `(consumer_id, kafka_partition, kafka_offset)`; `CHECK` constraints on `failure_code` against the exact Python allowlist, on `replay_state`, on `replay_claim_token` matching `^[0-9a-f]{64}$` when non-NULL, on `first_failed_at <= last_failed_at`, and on `created_at <= updated_at`) and `consumer_dead_letter_replay_attempts` (foreign key to the dead-letter row; `CHECK` on `status`; on `request_fingerprint`/`ownership_token` each matching `^[0-9a-f]{64}$`; on `created_at <= finished_at` when non-NULL; unique `(dead_letter_id, idempotency_key)`). `processing_attempt_count` (attempts before dead-lettering) and `dead_letter_delivery_count` (redeliveries of an already-dead-lettered record) are tracked separately; the `upsert` conflict path increments only the latter, leaving every first-insert retained field untouched.
- Replay fencing (`atlas.persistence.repositories.consumer_dead_letter.DeadLetterReplayService`) runs three transactions per replay attempt. TX1 (claim): locks the DLQ row, then reads its authoritative clock — only *after* that lock is acquired, for the same reason as TX2/TX3 below — before validating `replay_eligible` and resolving `(dead_letter_id, idempotency_key)` against that fresh reading: same key + different fingerprint is `ReplayConflictError`; same key + same fingerprint + live claim returns the existing `IN_PROGRESS` attempt; same key + same fingerprint + expired claim marks that attempt `LOST_OWNERSHIP` (using the fresh time as `finished_at`) and requires a fresh key; a fresh key may claim an unclaimed `PENDING`/`REPLAY_FAILED` row or reclaim an expired `REPLAYING` row (marking the previous token's attempt `LOST_OWNERSHIP`, again at the fresh time, first) and atomically installs a new `IN_PROGRESS` attempt — with `created_at` set to the fresh time — with a new ownership token and a `consumer_replay_lease_seconds` (default 90s) lease computed from that same fresh time — starting the lease from a timestamp taken after the row lock is acquired avoids consuming any of the lease's duration while TX1 was waiting for that lock, though it does not by itself guarantee the lease cannot expire before TX1 commits (an exceptionally delayed transaction could still consume lease time between that reading and commit); TX2 and TX3 do not rely on this reading alone and independently recheck the lease after their own row locks, failing closed if it has by then expired. TX2 (apply) and TX3 (record failure) both read the clock only *after* acquiring their row locks (`with_for_update=True`) — lock acquisition can block for an unbounded time, and a clock reading taken beforehand could stale-pass a lease that expired while waiting — and both require, at that fresh post-lock time, the exact ownership token, `IN_PROGRESS`/`REPLAYING` status, and an unexpired lease; an expired-but-not-yet-reclaimed owner is ownership already lost in either transaction (never applies the effect, marks `FAILED`, clears the claim/lease, or overwrites a result — it falls through to the same `LOST_OWNERSHIP` handling a genuine token mismatch produces, and a future reclaimer's own TX1 remains free to take over). TX2 locks the DLQ row `FOR UPDATE`, decodes the retained canonical event, applies it, and atomically finalizes the attempt (`APPLIED`/`DUPLICATE`) and the DLQ row (`REPLAYED_APPLIED`/`REPLAYED_DUPLICATE`), clearing the claim; only an exact allowlisted set of expected failures (`DomainEventError`, a SQLAlchemy `DBAPIError`, `ConsumerInboxConflictError`, `LifecycleOrderViolationError`) is caught and routed to TX3 as an ordinary sanitized `FAILED` outcome — any other exception (a programming defect in this service or a collaborator) propagates out of `replay()` uncaught, and TX2's rollback leaves the attempt row `IN_PROGRESS` rather than misrecording it as a routine business failure. TX3 (record failure): after a TX2 rollback, a fresh transaction marks the DLQ row `REPLAY_FAILED` and the attempt `FAILED` only if the same token is still valid (same unexpired-lease requirement as TX2); if ownership was already lost, only the stale attempt is conditionally marked `LOST_OWNERSHIP` and the DLQ row is left untouched. Neither TX2 nor TX3 ever calls `session.rollback()` inside a caller-owned transaction — `session_scope` owns commit/rollback for each of the three transactions.
- The local-only operator CLI (`python -m atlas.consumer.replay`) is the sole replay boundary — there is no HTTP replay endpoint. It accepts a bounded DLQ id, actor id, reason, and optional idempotency key (generated and logged if omitted); actor identity is self-asserted under the documented temporary trusted-shell boundary. It never deletes or bypasses inbox rows (an inbox duplicate is a successful no-op) and never mutates projection/inbox state to manufacture replay eligibility — a lifecycle-order-violation replay that is still invalid requires a separately authorized correction, not a CLI side effect. Output and exit codes are sanitized: no `str(exc)`/`repr(exc)`/exception args ever reach a log line or the process's own output. Like the consumer executable, it constructs its PostgreSQL engine via `atlas.consumer.db.build_consumer_engine` (not the shared cached singleton) so the same connect/pool/statement timeout bounds apply to a replay attempt's own database work.
- Database round-trip instrumentation (`atlas.persistence.instrumentation.count_database_round_trips`, test-only) observes SQL cursor executions, pool checkout/pre-ping, and DBAPI commit/rollback via real SQLAlchemy engine events — not `before_cursor_execute` alone. `consumer_max_db_round_trips_per_attempt=8` is an intentionally conservative cap; every current processing path (new-event apply, duplicate apply, lifecycle-violation apply, DLQ insert, DLQ conflict-upsert) measures below it.

This replaces the Slice 13C1-era Compose `kafka-topic-init` service, which called the broker image's own `kafka-topics.sh` shell script directly because no Python entry point existed yet; the new `kafka-topic-init` service now runs this typed executable inside the shared Atlas image instead.
- Internal networking is hardcoded, not `.env`-interpolated: every Atlas service's `ATLAS_DATABASE_URL`, `ATLAS_REDIS_URL`, and `ATLAS_KAFKA_BOOTSTRAP_SERVERS` is a literal string embedding the Compose-internal DNS name and container-internal port (`postgres:5432`, `redis:6379`, `kafka:9092` — all three are the same service names Compose already assigns automatic DNS entries for). None of these three keys is written as `${ATLAS_DATABASE_URL}`-style interpolation, so a developer's own host-oriented `.env` (which points at the *host-published* ports `127.0.0.1:5433`/`6380`/`9094` for host-run processes and tests) has no mechanism to override them: Compose variable substitution only ever applies where a compose value is itself written as `${...}`. No Atlas service uses `env_file: .env` (which would inject every key present in that file into the container wholesale, including any future, unrelated secret added to it later, and would also require excluding the internal-DNS keys some other way). Instead, exactly three optional third-party credentials (`ATLAS_OPENAI_API_KEY`, `ATLAS_ANTHROPIC_API_KEY`, `ATLAS_TAVILY_API_KEY`) are each individually named and mapped as `${VAR:-}` (empty default) on the `api` and `worker` services only — the two services whose code paths can read them — so enabling a live provider later only ever requires setting that one named variable in the developer's shell or Compose `.env`, and no other key can leak through. The `outbox-relay`/`consumer`/`db-migrate`/`kafka-topic-init` services never reference any of the three credentials at all, since none of their code paths read them. Compose keeps publishing PostgreSQL/Redis/Kafka on their existing host ports (`127.0.0.1:5433`/`6380`/`9094`) for host-run processes and tests, unaffected by this slice, and additionally publishes the API at `127.0.0.1:8000:8000` only.
- Hardening is defined once via a second shared YAML anchor, `x-atlas-hardening`, merged into every one of the six Atlas services with a `<<:` YAML merge key: `read_only: true`; `tmpfs: [/tmp]` (the one writable path the image's runtime processes need, supplied externally rather than by relaxing the read-only root); `cap_drop: [ALL]` (verified empirically: none of the six services need any Linux capability — no port below 1024, no raw sockets, no privileged syscalls); `security_opt: [no-new-privileges:true]`. The image's own non-root `USER atlas` (Slice 14A) is never overridden by any service's `user:` key. No service mounts the source tree, a `.env` file, or the Docker socket; none sets `privileged: true`; no service places a literal credential value directly in the compose file (the three optional credentials above are always sourced from the environment, never hardcoded). This hardening was validated empirically, not just declared: `alembic upgrade head` completed successfully under `read_only: true` + `tmpfs: [/tmp]` + `cap_drop: [ALL]`, and all four long-running roles started and ran without any permission-denied or read-only-filesystem error in their logs.
- Dependency ordering uses only `depends_on` health/completion conditions, never a sleep: `db-migrate` depends on `postgres: {condition: service_healthy}`; `kafka-topic-init` depends on `kafka: {condition: service_healthy}`; `api` and `worker` each depend on `db-migrate: {condition: service_completed_successfully}` **and** `redis: {condition: service_healthy}` (neither needs Kafka directly; the `redis` dependency is Compose startup sequencing only — added because both services explicitly set `ATLAS_COORDINATION_PROVIDER=redis`, and it does not change Atlas's own runtime fail-open behavior on any later Redis error); `outbox-relay` and `consumer` each depend on both `db-migrate` and `kafka-topic-init` completing successfully (both need PostgreSQL and Kafka). This was observed directly: bringing up all six Atlas services in one `docker compose up -d` command re-ran (idempotently) and waited for both one-shot jobs to exit `0` before creating any long-running service's container. `api` has its own Compose `healthcheck:` (`python -c "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/health', timeout=3)"` — there is no `curl`/`wget` in the minimal runtime image, so this uses the stdlib already on `PATH`) purely for `docker compose ps` operator visibility; no `depends_on` condition anywhere in the file consults it, and worker/outbox-relay/consumer health is always verified independently (the worker's own Redis heartbeat key; the outbox relay's/consumer's own effect on PostgreSQL/Kafka state) — API health is never treated as a proxy for their health, per the approved design.
- Compose shutdown budgets (`stop_grace_period`), each independently derived from the corresponding role's own existing bounded shutdown behavior rather than picked arbitrarily: API `15s` (the Dockerfile's default `CMD` now explicitly bounds uvicorn's own graceful-shutdown-then-re-raise behavior, Slice 14A, at `--timeout-graceful-shutdown 10`, plus `5s` headroom for signal forwarding/teardown, rather than relying on uvicorn's undocumented default); worker `75s` (`worker_processing_timeout_seconds` defaults to `60s`, which is also `ResearchJobWorker`'s default `shutdown_grace_seconds`, plus `15s` headroom); outbox relay `30s` (not derived from `outbox_publish_lease_seconds` — that lease is a fencing/crash-recovery constraint on reclaim eligibility, not an additive graceful-shutdown step, and shutdown never waits for it to expire; the relay's `_cleanup()` instead bounds an in-flight record's publish by `kafka_delivery_timeout_seconds`, default `10s`, then bounds the producer's own `close()`/flush by that same `10s` setting again, plus headroom for advisory-lock release, signal-handler restoration, and process scheduling); consumer `300s` (equal to `consumer_max_poll_interval_seconds`'s default, the outer bound the consumer's own bounded per-record retry/backoff is validated to stay safely under). Kubernetes will independently rederive its own termination-budget values in Milestone 18 rather than inheriting these Compose-specific numbers verbatim.
- Local end-to-end verification (fake model/tool/embedding providers throughout; no live OpenAI/Anthropic/Tavily/embedding/LangSmith network call was made — confirmed by the resulting report's findings containing only `https://example.com/fake/...` URLs) proved the full application-transaction → PostgreSQL outbox → Kafka → consumer inbox → lifecycle-projection path end-to-end against real Compose-started PostgreSQL/Redis/Kafka: a submitted research job reached `COMPLETED`; both its `research_job.created` and `research_job.completed` outbox rows were published; both corresponding `consumer_inbox` rows existed under the fixed consumer id; and `research_job_event_projection` recorded the terminal `research_job.completed` event for that job — inspected directly in PostgreSQL, not inferred from the API response alone. `Idempotency-Key` replay (`202`, same job id) and conflict (`409`) behavior were unaffected. All four long-running services stopped promptly and cleanly on `SIGTERM` while idle, well inside their configured budgets (API `~1s`/`ExitCode=143`, re-verified after adding the explicit `--timeout-graceful-shutdown 10` bound; outbox relay `~1s`/`ExitCode=0`; consumer `~2s`/`ExitCode=0`; worker `~0s`/`ExitCode=0`), and the stack (including its volumes) was torn down after verification. A companion `tests/test_docker_compose_contract.py` (4 tests) statically renders `docker compose config --format json` and asserts the single-`build:`/shared-image-tag/no-`ENTRYPOINT`-override/Redis-dependency invariants described above, so a future edit that reintroduces a duplicate `build:` or drops the `redis` dependency fails a fast, network-free test rather than only being caught by manual inspection.

### Container CI: build-once, structural checks, and supply-chain evidence (Milestone 14 Slice 14C)

- `.github/workflows/containers.yml` is a separate, single-job workflow from the existing `.github/workflows/ci.yml` (which never touches Docker). It triggers on pull requests and on pushes to `main`; declares `permissions: contents: read`; cancels superseded runs of the same ref via `concurrency: {group: containers-${{ github.workflow }}-${{ github.ref }}, cancel-in-progress: true}`; and bounds the whole job at `timeout-minutes: 25`.
- Build-once, then verify identity before every later phase: the job resolves `GIT_SHA` via `git rev-parse HEAD` on the actual checked-out tree — deliberately not `github.event.pull_request.head.sha`/`github.sha`, because for a `pull_request` trigger `actions/checkout`'s default ref is GitHub's own PR merge commit (the PR branch tip merged onto its base), a different revision than `head.sha`. The workflow validates whatever tree is actually checked out and labels it with that exact revision everywhere: the image tag, the OCI `revision` label, `BUILD_DATE` (`git show -s --format=%cI "$GIT_SHA"` — that revision's own commit timestamp, never the workflow's wall-clock run time, matching the Slice 14A OCI-label design), image-identity evidence, artifact names, and the E2E idempotency key. It then runs exactly one `docker buildx build --load --provenance=false --sbom=false --tag atlas-backend:$GIT_SHA --build-arg GIT_SHA=$GIT_SHA --build-arg BUILD_DATE=$BUILD_DATE --cache-from type=gha --cache-to type=gha,mode=max,ignore-error=true .`. `--provenance=false --sbom=false` disables BuildKit's own build-time attestation manifests: they are not guaranteed compatible with `--load` on every runner's image-store configuration, and this repository's own Syft-generated SBOM (below) is the intended single source of truth, not a build attestation. `ignore-error=true` on cache export means a transient GitHub Actions cache-service failure can only degrade this build's performance (it falls back to a fully cold build); it can never fail an otherwise valid build. Cache import (`--cache-from`) needs no equivalent flag because a missing or failed cache import already fails open to a cold build by design. Immediately after the build, the job records `docker image inspect atlas-backend:$GIT_SHA --format '{{.Id}}'` and re-checks that the tag still resolves to that same recorded ID before structural checks, before infrastructure startup, before application-service startup, and before Syft/Trivy — proving by direct measurement, at each phase, that nothing later in the job silently rebuilt or replaced the image. It additionally verifies, immediately after Compose starts each of the six Atlas services in turn (`db-migrate`, `kafka-topic-init`, `api`, `worker`, `outbox-relay`, `consumer`), that the specific container Compose created for that service (`docker inspect <container> --format '{{.Image}}'`) resolves to that same recorded image ID — proving each service actually ran the one image built in this job, not merely that the tag was not reassigned. No step after the single build ever runs `docker compose build` or passes `--build`; every Compose command in the job resolves the already-built local image through the existing `image: *atlas-backend-image` reference in `docker-compose.yml` — by construction, Compose only rebuilds an image when it is missing locally or `--build`/`pull_policy: build` is requested, neither of which applies here.
- Reproducibility claim, precisely bounded: pinned base-image digests (Slice 14A), the frozen `uv.lock`, and this commit's own exact source tree make the build **functionally/content-equivalent** on every run of the same commit — this workflow does not claim, and does not depend on, strict byte-for-byte image-digest reproducibility. The `docker/setup-buildx-action`-provisioned `docker-container` driver's `type=gha` cache backend can only change how long the build takes (a cache hit skips re-executing unchanged layers); it never changes what the build produces, since every layer's inputs are identical regardless of cache state.
- `docker/setup-buildx-action` is required (not merely convenient) because the default `docker` buildx driver on a GitHub-hosted runner does not support exporting to the `type=gha` cache backend — only the `docker-container` driver this action provisions does.
- Structural checks (all run against the built `atlas-backend:$GIT_SHA` via `docker run`/`docker image inspect`, before any Compose service starts): Python version (`Python 3.12.*`); `atlas`/`atlas.main`/`atlas.worker`/`atlas.outbox`/`atlas.consumer`/`atlas.outbox.topic_admin` all import; non-root identity (`uid=10001(atlas) gid=10001(atlas)`); `pytest`/`mypy`/`ruff` all absent (`importlib.util.find_spec` returns `None` for each); no `uv` binary on `PATH` and no `/app/src` directory; the four required OCI labels present and `org.opencontainers.image.revision` exactly equal to `$GIT_SHA`; and (GitHub Actions `ubuntu-latest` only — not reproducible on an Apple Silicon development machine, which legitimately builds `linux/arm64` for the same Dockerfile) `docker image inspect --format '{{.Os}}/{{.Architecture}}'` equals `linux/amd64`. Two additional static checks run directly against the `Dockerfile` source, independent of any build: both base-image `FROM` lines are digest-pinned, and exactly two `--checksum=sha256:` Tini fetches exist (one per architecture).
- Runtime smoke sequence reuses the Slice 14B Compose topology verbatim, run against the exact image identified above: bring up `postgres`/`redis`/`kafka` and wait for health; run `db-migrate`/`kafka-topic-init` as one-shot jobs and gate on their exit codes (`docker compose up <service> --exit-code-from <service>`); start `api`/`worker`/`outbox-relay`/`consumer` and wait for health; assert `/health` and `/ready` both return `200`; assert the worker's Redis heartbeat key exists and its TTL is higher after a short sleep than a naive linear decay would predict (proving refresh, not just presence); submit one fake-provider research job via `POST /v1/research-jobs`, parse and validate the response `id` as a well-formed UUID (before it is ever interpolated into a SQL query in any later step), and poll `GET /v1/research-jobs/{id}` to a bounded terminal deadline asserting `status == "COMPLETED"`. Before any replay, the job records and asserts baseline invariants directly against PostgreSQL for that job id: exactly one `research_jobs` row; exactly one published `research_job.created` outbox event and exactly one published `research_job.completed` outbox event (an explicit exactly-once check per event type, not a numeric lower bound alone — this is what actually rules out a vacuous pass below, since it forces the distinct published-event count to be at least 2 whenever this check itself does not already fail); exactly one `research_job_event_projection` row with `last_event_type == "research_job.completed"`; zero duplicate `(consumer_id, event_id)` keys in `consumer_inbox` for the projection consumer; and the projection consumer's distinct inbox `event_id` count equal to the distinct published `outbox_events.event_id` count for that job (both computed with explicit `count(DISTINCT event_id)` semantics, so the comparison cannot be satisfied by a vacuous `0 == 0`). It then replays the identical `Idempotency-Key`/body and asserts HTTP `202`, the same job id in the replay response body, and all recorded counts unchanged; it then replays the same key with a changed body and asserts HTTP `409` and again that all counts remain unchanged. Only counts, statuses, and job ids are ever printed — never full response bodies or environment data.
- Bounded idle shutdown, deliberately decoupled from each service's own (much larger, busy-case) `stop_grace_period`: for each of `api`/`worker`/`outbox-relay`/`consumer`, the job runs `timeout 20 docker compose stop -t <that service's configured stop_grace_period> <service>`. The `-t <grace>` argument still governs Compose's own real internal SIGTERM-then-wait-then-SIGKILL escalation exactly as `docker-compose.yml` declares it; the outer `timeout 20` is a CI-side observation deadline sized for the specific case this check exercises — an **idle** service, which Slice 14B's manual evidence showed stops in well under 2 seconds for all four roles — not a re-derivation of the (much larger) busy-case grace periods those services are entitled to when actually mid-work. If a service hangs, `timeout` fails that one step (not the whole job), and execution still proceeds to the unconditional teardown step below.
- Supply-chain evidence, generated against the exact same local image (never re-pulled or rebuilt): `anchore/sbom-action` (pinned, `syft-version: v1.42.3` explicitly pinned as an action input) runs that exact Syft release to produce a CycloneDX JSON SBOM, uploaded as a workflow artifact retained 30 days. Trivy (via `aquasecurity/trivy-action`, pinned, `version: v0.70.0` explicitly pinned as an action input on all three invocations) scans the same image three times, each with a distinct purpose: once with `format: table`, `exit-code: "0"` (always succeeds; readable log only); once with `format: json`, `exit-code: "0"`, `output` written to a file uploaded as a 30-day artifact with `if: always()` (so evidence survives even when the next step fails); and once as the actual enforcement gate — `severity: HIGH,CRITICAL`, `vuln-type: os,library`, `ignore-unfixed: true` (explicit, documented, and the only mechanism used for unfixed findings — there is no `.trivyignore` file anywhere in the repository), `exit-code: "1"`. No SARIF output is produced or uploaded in this slice.
- Cleanup and sanitization: `docker compose down -v --remove-orphans` runs with `if: always()` as the job's final step, so Compose containers, the network, and both infrastructure volumes are removed regardless of which earlier step failed. No step in the workflow prints a rendered `docker compose config`, an environment dump, a credential, a provider key, a complete API response body, or a raw database URL; job output that could plausibly contain such values (subprocess failures, JSON parsing errors) is deliberately reduced to a fixed sanitized message rather than the raw output.
- Every third-party action is pinned to a full commit SHA with a version comment rather than a floating tag: `actions/checkout` (reused from `ci.yml`'s existing pin), `docker/setup-buildx-action`, `anchore/sbom-action`, `aquasecurity/trivy-action` (used three times), and `actions/upload-artifact`. Beyond the Action's own commit SHA, three of these also explicitly pin the underlying tool version they install, rather than relying on that pinned Action's own default: `docker/setup-buildx-action` takes an explicit `version: v0.36.1` Buildx release; `anchore/sbom-action` takes an explicit `syft-version: v1.42.3`; and all three `aquasecurity/trivy-action` invocations take an explicit `version: v0.70.0` (this happens to already equal that pinned Action's own default, but is stated explicitly rather than left implicit).
- Explicitly out of scope for this slice, matching the approved proposal: registry publication, image signing/attestation, SARIF upload, deployment promotion (all remain Milestone 23); Kubernetes/Helm (Milestone 18); Terraform/AWS; and the broader Milestone 16 source/dependency/secret/IaC security workflow.

### Structured JSON logging and correlation context (Milestone 15 Slice 15A1)

- One centralized module, `src/atlas/observability/logging.py`, is the only place in Atlas that decides what a log line looks like. `configure_logging(service_role=...)` installs a single `AtlasJSONFormatter`-backed `StreamHandler` on the root logger and applies a fixed third-party logger policy (below); it is idempotent (a repeat call only ever removes the handler it itself previously installed, never a handler installed by anything else — in particular, never a test harness's own `caplog` handler) and is called exactly once, as early as possible, in each of the five converted entrypoints (`atlas.main`, `atlas.worker.__main__`, `atlas.outbox.__main__`, `atlas.consumer.__main__`, `atlas.outbox.topic_admin`), replacing each entrypoint's previous `logging.basicConfig(...)` call.
- Two deliberately distinct line shapes, never conflated, and **both fully sanitized** (a correction from an earlier revision that rendered the second shape's raw message/logger name — see below): an **Atlas-structured** line (created only via `log_event`/`log_exception_boundary`) carries exactly the fixed approved field set below and nothing else — no message text, no arbitrary `extra`, no traceback, no stack info; a **legacy/third-party** line (every other record — an unconverted Atlas call site, or a third-party library logger) renders as exactly `timestamp`/`severity`/`service`/`event` (always the fixed `Event.UNSTRUCTURED_LOG_SUPPRESSED`)/`logger_category` — a normalized, closed-allowlist category (`uvicorn`, `psycopg`, `httpx_httpcore`, `redis`, `sqlalchemy`, `atlas_unconverted`, or `other`) derived from `record.name` by prefix match, never the raw logger name itself. `AtlasJSONFormatter` never reads `record.getMessage()`, `record.msg`, `record.args`, `record.exc_info`, `record.stack_info`, or any `extra` attribute for a non-Atlas-structured record — there is no message left to sanitize or fail to sanitize. Atlas records only that an approved third-party/unconverted signal *occurred*, its category, and its severity, never its original content.
- Approved Atlas-structured JSON fields (always all present, `null` when unset — the schema is identical on every line, never variable-shaped): `timestamp`, `severity`, `service`, `event`, `trace_id`, `span_id`, `research_job_id`, `workflow_execution_id`, `node_name`, `model_invocation_id`, `tool_invocation_id`, `evaluation_run_id`, `outbox_event_id`, `consumer_event_id`, `error_class`, `duration_ms`, `outcome`. `trace_id`/`span_id` are always `null` in this sub-slice by construction — no call site anywhere sets them; Slice 15A2 (OpenTelemetry) is what populates them, once it exists.
- `Event(StrEnum)` (`src/atlas/observability/events.py`) is the fixed, closed set of event names — there is no f-string/free-text event-name path anywhere: `log_event`/`log_exception_boundary` reject (`TypeError`) anything that is not an `Event` member before any serialization happens. The set is deliberately coarse-grained (`PROCESS_STARTED`, `PROCESS_STOPPED`, `SIGNAL_RECEIVED`, `STARTUP_FAILED`, `STARTUP_VERIFICATION_FAILED`, `SHUTDOWN_CLEANUP_FAILED`, `POLL_LOOP_RECOVERABLE_ERROR`, `POLL_LOOP_TERMINAL_ERROR`, `POLL_LOOP_SHUTDOWN_DURING_BACKOFF`, `READINESS_CHECK_FAILED`, `TOPIC_ADMIN_SUCCEEDED`): the `service` field (set once per process by `configure_logging`) already identifies which process role emitted a line, and `error_class`/`outcome`/business-ID fields already carry what specifically happened, so a near-duplicate event per source file/failure would not add real information.
- `log_event(logger, event, *, level=logging.INFO, **fields)` validates every keyword against a fixed field allowlist (`ValueError` naming only the offending field, never its value, if violated) and every value's type (`str`/`int`/`float`/`bool`/`None` only — `TypeError` otherwise, so an exception object itself can never be passed as a field value and silently stringified). An oversized string field is truncated at 256 characters (with a `...<truncated>` suffix), never rejected. `log_exception_boundary(logger, event, exc, *, level=logging.ERROR, **fields)` derives `error_class` from `exc.__class__.__name__` only — its signature has no parameter through which `str(exc)`/`repr(exc)`/`exc.args`/`exc_info`/`stack_info` could reach a rendered line, and passing an explicit `error_class=` override is rejected. `AtlasJSONFormatter.format()` never calls `self.formatException` and never reads `exc_info`/`stack_info` on either the structured or legacy code path — proven even when a raw stdlib call is made with `exc_info=True`.
- Third-party logger policy (`configure_logging`'s `_configure_third_party_loggers`, chosen from what this codebase's actual installed dependencies do, not assumed) controls **level and routing** only — it never changes what a record renders as, since every record reaching `AtlasJSONFormatter` is already reduced to the fixed shape above regardless of which policy bucket its logger falls into. `uvicorn.access` is suppressed entirely (`propagate=False`, handlers cleared) before it ever reaches the formatter, because even a `logger_category`-reduced but high-volume access-log signal could leak request timing/frequency information this sub-slice has not evaluated. `uvicorn`/`uvicorn.error` are kept but rerouted through Atlas's own formatter (`propagate=True`, their own handlers cleared) as the fixed `"uvicorn"` category. `psycopg.pool` is raised to `ERROR` (from its default `WARNING`) since Atlas's own sanitized error handling at each call site already reports the same condition safely. `httpx`/`httpcore`/`redis` are raised to `WARNING` defensively (currently inert, since root is already `INFO`, but explicit against a future accidental `DEBUG`-level enable — relevant because Atlas's Tavily search tool sends the search query as part of the request URL; even if triggered, only the fixed `"httpx_httpcore"` category would render, never the URL). `sqlalchemy.engine` is held at `WARNING` defensively (no `create_engine` call anywhere in this codebase passes `echo=True` today). `confluent_kafka` is deliberately not configured here at all: verified directly that no Atlas Kafka client (`atlas.outbox.kafka_producer`, `atlas.consumer.kafka_consumer`) passes a `'logger'` callback into its client configuration, so librdkafka's own diagnostics never enter Python's `logging` module in the first place. Remaining Atlas-owned, not-yet-converted `logger.*` call sites (`atlas.api.errors`, `atlas.application.worker`, `atlas.consumer.replay`, `atlas.outbox.relay`, `atlas.coordination.outage_log`, `atlas.coordination.heartbeat_thread` — verified by repository-wide search) render as the fixed `"atlas_unconverted"` category; whatever message/args/`exc_info` any of them pass is structurally unable to reach a rendered line, independent of whether that call site's own text happens to already be sanitized.
- `contextvars`-based Atlas business correlation context (`src/atlas/observability/context.py`: `bind_context`, `current_context`, `ALLOWED_CONTEXT_FIELDS`) binds a fixed, closed set of opaque correlation identifiers (the correlation-shaped subset of the approved field list above, i.e. every field except `error_class`/`duration_ms`/`outcome`) so a bound log line automatically carries them without every call site threading the values through explicitly. Nesting merges with (never replaces) the enclosing context and restores it exactly on exit via `contextvars.Token`-based reset, including after an exception raised inside the block. `asyncio.Task`s copy `contextvars` values at creation time (the standard library's own guarantee, not something this module implements), so two concurrently running tasks that each bind independently never observe each other's values; a plain `threading.Thread` does **not** inherit a bound context — a new native thread always starts empty, and anything handing work to a plain thread must re-bind context from inside that thread's own callable if it wants correlation fields to apply there too. Values are opaque and bounded at the same 256-character limit `log_event` itself enforces (truncated, never rejected, never parsed/format-validated). `current_context()` returns a `types.MappingProxyType` view over the internally stored `dict`, never the mutable `dict` itself — mutating the returned object raises `TypeError`; the only supported way to change what a later `current_context()` call observes is `bind_context()` itself (a correction from an earlier revision that returned the mutable dict directly, type-annotated as `Mapping` but not actually enforced immutable at runtime). No production call site binds context yet in this sub-slice — documented directly in the module's own docstring: none of the entrypoint-level boundaries converted this sub-slice has a per-job/per-message business identifier available at the point it runs; that identifier exists one layer deeper (`atlas.application.worker`, `atlas.consumer.runner`), which is out of this sub-slice's explicit call-site-conversion scope and arrives with a later slice's tracing/business-logging work.
- Strict JSON-safe numeric values: `json.dumps(..., allow_nan=False)` is used for every rendered line (defense in depth, independent of the validation below, against a record ever being constructed by a path that bypasses it). At `log_event`'s own field-validation boundary, `_validate_field_value` rejects `NaN`/`Infinity`/`-Infinity` for any numeric field, and additionally rejects a negative `duration_ms` specifically (a duration cannot be negative); finite non-negative integer/float durations continue to be accepted unchanged. Rejection is always a `ValueError` naming only the field, never the rejected value, raised before anything is serialized.
- Converted call sites (startup/shutdown/signal/poll-loop boundaries only — not a repository-wide rewrite): the API's logging setup and `/ready`'s `SQLAlchemyError` path (`atlas.main`); the worker, outbox-relay, Kafka-consumer, and Kafka-topic-admin entrypoints' startup/shutdown/signal/poll-loop boundaries (`atlas.worker.__main__`, `atlas.outbox.__main__`, `atlas.consumer.__main__`, `atlas.outbox.topic_admin`). Existing exit codes, error classification, retry behavior, and shutdown behavior are unchanged in every converted file — only the logging call itself changed at each site. Deeper call sites (domain/application/workflow/tool/model logging, and any future per-request/per-job/per-message logging) remain unconverted and are not claimed to be covered by this sub-slice.
- No new third-party dependency was introduced: the Python standard library (`logging`, `contextvars`, `enum.StrEnum`, `json`) is sufficient for this sub-slice's scope. Lightweight static typing plus a runtime allowlist (not a Pydantic model per log event) was used deliberately — no repository evidence demonstrated a need for per-event runtime schema validation beyond the fixed field/type allowlist `log_event` already enforces directly.

## Planned architecture decisions (approved ahead of implementation)

These decisions are approved and govern how Milestone 15 (and later milestones) must be built, but nothing described in this section is implemented yet except where a later slice's own dedicated section above states otherwise (Slice 15A1's structured-logging/correlation-context design is documented above, not here, since it is now implemented). They are recorded now, ahead of implementation, so later work does not have to re-litigate them; do not treat any capability named here as existing until `PROJECT_STATE.md` records it as built and verified.

### Mandatory LangSmith AI observability (Milestone 15 Slice 15B)

- LangSmith is **mandatory** for Atlas AI observability and must never be described or implemented as optional.
- Scope split: LangSmith is mandatory for LangGraph/LLM/RAG/tool/evaluation observability. OpenTelemetry (Slice 15A2), Prometheus/Grafana/Alertmanager (Slice 15A3), and structured logging (Slice 15A1, implemented — see above) remain mandatory for infrastructure and distributed-system observability. LangSmith does not replace operational monitoring, and operational monitoring does not replace LangSmith — they cover different concerns.
- Availability: LangSmith must never become an availability dependency. A LangSmith export outage must not fail a research job; the failure must be caught, logged (sanitized), and reflected in operational metrics instead.
- Testing: local/offline tests must not require a real LangSmith API key. Contract tests use fakes/mocks. At least one explicit opt-in live integration test must prove traces actually appear in a real LangSmith project. A simulated LangSmith outage test must prove research continues and the failure is handled safely.
- Data safety: no API keys, raw secrets, unrestricted evidence, or unsanitized exception text may ever be exported to LangSmith. A documented trace-data/redaction policy must define exactly which prompts, responses, evidence, and metadata may be sent before any trace is exported.
- Correlation: LangSmith trace identifiers must correlate safely with Atlas's own durable identifiers — job, workflow execution, node execution, model invocation, tool invocation, and evaluation — without leaking sensitive data through that correlation.

### Live semantic grader, held-out calibration, and the bounded advisory analyst (Milestone 15 Slice 15C)

- A live LangChain semantic groundedness grader, with durable semantic-grading results persisted in the Atlas evaluation system, and an independent held-out human-labeled validation set used to calibrate it.
- Evaluation freeze discipline: landing the live semantic grader under Slice 15C does not automatically freeze `evaluation.v1`. `evaluation.candidate.v1` remains provisional until the documented held-out/live-semantic calibration gate passes; freezing `evaluation.v1` is then a separate, explicitly reviewed decision (see Milestone 12's existing provisional-profile decisions above).
- The analyst consumes only sanitized, bounded telemetry summaries — never unrestricted raw production data (logs, traces, or database rows) directly.
- Allowed: summarizing incidents, clustering recurring failures, suggesting likely causes/remediation, and explaining job/agent/model/tool/retrieval/Kafka/evaluation failures in natural language.
- Forbidden, with no exceptions: restarting workloads, retrying jobs, changing configuration, modifying prompts, deploying code, acknowledging alerts, mutating database state, or invoking infrastructure APIs.
- Deterministic Prometheus/Alertmanager rules remain the authoritative monitoring control plane; the advisory analyst is read-only and advisory only, never a substitute for or override of that control plane.
