## Objective

Build a production-oriented deep-research platform that provides interview-defensible experience in applied AI, backend/distributed systems, reliability, observability, delivery, and AWS infrastructure.

## Current direction

A user submits a complex research request. Atlas creates a durable job, plans bounded work, coordinates specialist agents and governed tools, gathers evidence, produces a cited report, grades the result, applies controlled recovery, and exposes progress, quality, cost, and operational diagnostics.

- Real Kafka outbox relay (Milestone 13 Slice 13C1, **Complete** through Pull Request #21 `cd5b25e`): pinned `apache/kafka:4.3.1` broker (Compose single-node KRaft, CI service container); `atlas.outbox.kafka_producer.KafkaEventProducer` implements `EventProducer` using `confluent-kafka>=2.15.0,<3` with hardcoded `acks=all` / `enable.idempotence=true`, bounded delivery/socket/request timeouts, and an explicit delivery callback — success requires callback invocation, `err is None`, and a zero `flush()` result. Every observed `KafkaError` (delivery callback, immediate `produce()`, or `flush()`) is classified by the single centralized `atlas.outbox.kafka_errors.classify_kafka_error` helper using only the error's own flags/code, never a string or exception-class match, per a narrow, fail-closed policy: `error.fatal()` → fatal; else `error.retriable()` → recoverable; else `error.code() == KafkaError._MSG_TIMED_OUT` → recoverable as a single, narrow, evidence-backed Atlas-specific exception (a delivery timeout only proves Atlas did not receive broker-confirmed delivery within the configured deadline, not that the broker never received the record; it is treated as recoverable at the durable-outbox level even though `retriable()` is `False`, consistent with Atlas's documented at-least-once contract — a later retry may duplicate the record on the topic, handled by the stable `event_id` plus the consumer inbox/deduplication implemented in Slice 13C2A); every other nonfatal, nonretriable error (e.g. `_BAD_MSG`) → fatal; an unrecognized/non-`KafkaError` payload → fatal. Fatal classification raises `KafkaFatalProducerError` and permanently closes the producer; recoverable classification raises `KafkaPublishError`/`KafkaPublishTimeoutError` and leaves the producer usable. `atlas.outbox.topic_admin` is a typed `AdminClient` helper that creates/verifies the fixed reserved topic (never an arbitrary runtime name) with exactly one partition, failing closed on an unreachable broker, a missing topic, or an incorrectly partitioned existing topic. `OutboxRelay.run_once()` now returns a typed `RelayBatchResult` (`RelayRunOutcome`: `EMPTY | PUBLISHED | RECOVERABLE_FAILURE | FATAL_FAILURE | OWNERSHIP_LOST | UNEXPECTED_FAILURE`) instead of a bare integer. The executable `python -m atlas.outbox` is Kafka-only (never constructs `FakeEventProducer`), always uses `batch_size=1`, verifies broker connectivity and topic partitioning before polling, backs off on recoverable outcomes, and terminates nonzero on a fatal or unexpected producer error or an unexpected PostgreSQL/lock error. `kafka_delivery_timeout_seconds + kafka_delivery_timeout_lease_margin_seconds <= outbox_publish_lease_seconds` (defaults 10s / 5s / 30s) is enforced at `Settings` construction. No lease renewal, no consumers, no inbox/dedup, no DLQ, and no Redis caching are added in this slice.
- Business Kafka consumer + inbox deduplication + lifecycle projection (Milestone 13 Slice 13C2A, **Complete** through Pull Request #22 `9f2b7af`): `atlas.consumer.kafka_consumer.KafkaEventConsumer` subscribes to the reserved topic under one fixed, allowlisted consumer group (`atlas.research-job-projection.v1`; `ALLOWED_CONSUMER_GROUP_IDS` rejects any other), with `enable.auto.commit=false` and offsets committed synchronously, once, only after the record's PostgreSQL transaction has committed. `atlas.consumer.deserialize.decode_message` strictly validates Kafka headers against the decoded envelope's own `event_type`/`event_version`/`aggregate_type` and fails closed on missing/duplicate/undecodable/unexpected headers, an oversized/undecodable value, malformed JSON, a non-object value, or a payload the typed research-job event catalog itself rejects. `consumer_inbox` (migration `20260809_0012`) has composite primary key `(consumer_id, event_id)`; `SqlAlchemyInboxRepository.record_and_apply` checks for a prior record, invokes the business effect only when absent, and inserts the inbox row in the same transaction — both commit together or neither does. A duplicate delivery skips the effect but the Kafka record is still acknowledged. The first business consumer, `research_job_event_projection` (also migration `20260809_0012`), is a durable, non-authoritative last-known-lifecycle read model keyed by `research_job_id`; once it records a terminal event (`research_job.completed`/`research_job.failed`), any *different* incoming event for that job raises `LifecycleOrderViolationError` rather than silently overwriting it (an exact redelivery of the same `event_id` never reaches this check — the inbox already short-circuits it as a duplicate). `ConsumerRunner.run_once()` orchestrates one poll-decode-apply-commit cycle; any error before offset commit propagates with the offset never acknowledged, so the record redelivers after restart. The executable `python -m atlas.consumer` has no HTTP surface (matches `python -m atlas.outbox`'s precedent) and needs no PostgreSQL advisory lock (Kafka's own consumer-group protocol already guarantees a single active reader of the topic's one partition).
- Consumer retry, poison-event dead-lettering, and operator replay (Milestone 13 Slice 13C2B, **Complete** through Pull Request #25, merge commit `865023b`): `ConsumerRunner` now retries only the in-hand record's PostgreSQL work (the apply transaction, or on poison classification the DLQ upsert) with deterministic exponential backoff (`atlas.consumer.timing`), bounded by a runtime `ProcessingDeadline` (message-received-at minus a safety margin) checked before every attempt and before every backoff sleep — `poll()` is never called again mid-retry, and the deadline is proven (by real-Kafka test) to fire well inside Kafka's own `max.poll.interval.ms`. Approved defaults (`consumer_retry_max_attempts=3`, `consumer_retry_base_seconds=1.0`, `consumer_retry_max_backoff_seconds=30.0`, `consumer_retry_jitter_max_seconds=0.0`, `consumer_retry_safety_margin_seconds=60.0`, `consumer_db_connect_timeout_seconds=5.0`, `consumer_db_pool_timeout_seconds=5.0`, `consumer_db_statement_timeout_seconds=5.0`, `consumer_retry_processing_overhead_seconds=2.0`, `consumer_max_db_round_trips_per_attempt=8`, `consumer_replay_lease_seconds=90.0`) compute to 52s per attempt / 219s total, under the 300s `consumer_max_poll_interval_seconds`; `Settings` rejects any combination that would not be. `atlas.consumer.errors` replaces every string-parameterized poison exception with a dedicated typed subclass carrying a fixed `failure_code` from an exact-type allowlist (`ALLOWED_FAILURE_CODES`); an unmapped subclass fails closed (`UnmappedPoisonEventTypeError`) rather than inheriting a parent's code. `atlas.consumer.db_classify.classify_database_error` treats only `connection_invalidated` or SQLSTATE class `08`/`40001`/`40P01` as transient (bounded retry); every other SQLSTATE, a missing SQLSTATE, and every `IntegrityError` (even with a transient-looking SQLSTATE) are fatal (immediate termination, no retry, no DLQ, no offset commit). Migration `20260809_0013` adds `consumer_dead_letters` (uniqueness boundary `consumer_id + kafka_partition + kafka_offset`; `CHECK`-constrained `failure_code`/`replay_state`; separate `processing_attempt_count` vs. `dead_letter_delivery_count`, the latter incremented only on redelivery conflict) and `consumer_dead_letter_replay_attempts` (`CHECK`-constrained `status`; unique `(dead_letter_id, idempotency_key)`). `atlas.consumer.retention.build_retention` retains a bounded canonical reserialization plus validated headers only for `lifecycle_order_violation` (`replay_eligible=true`); every other failure code retains only a SHA-256 hash and byte length of the raw value — never raw bytes — so oversized or otherwise untrusted poison is durably DLQ-able without storing anything attacker/producer-controlled. The offset is committed only after the DLQ row durably commits; a subsequent offset-commit failure (`OffsetCommitFailedAfterDeadLetterError`) terminates the process, and redelivery safely reuses the existing DLQ row via its uniqueness boundary. `DeadLetterReplayService` (`atlas.persistence.repositories.consumer_dead_letter`) runs three transactions per replay: TX1 claims the row with idempotency-key fencing (same key/different fingerprint conflicts; same key/live claim returns the existing attempt; same key/expired claim requires a fresh key; a fresh key may claim `PENDING`/`REPLAY_FAILED` or reclaim an expired `REPLAYING` row, marking the previous attempt `LOST_OWNERSHIP` first); TX2 locks the DLQ row, verifies the exact ownership token and an unexpired lease (a stale owner never applies the effect), decodes the retained canonical event, applies it via `InboxRepository.record_and_apply`, and atomically finalizes both the attempt and the DLQ row; TX3 records a replay failure in a fresh transaction after a TX2 rollback, distinguishing still-valid-ownership failure from lost-ownership. All three transactions read their authoritative clock only after acquiring the dead-letter row's lock, so a blocking lock wait can never leave a leasing/eligibility decision (or a newly installed lease's own expiration) based on stale, pre-lock time. `atlas.consumer.db.build_consumer_engine`'s libpq/PostgreSQL timeout conversions (and the matching `atlas.consumer.timing`/`Settings` timing-margin formulas) use ceiling rounding with a floor of 1 (`atlas.config.timeout_math`), so no positive configured connect/statement timeout can round down to a driver-level `0` ("no timeout"). The sole replay boundary is a local-only operator CLI, `python -m atlas.consumer.replay` (no HTTP endpoint): bounded DLQ id/actor id/reason/idempotency key, self-asserted actor identity under a documented temporary trusted-shell boundary, sanitized output/exit codes, and no ability to mutate projection/inbox state to manufacture eligibility. Test-only `atlas.persistence.instrumentation.count_database_round_trips` observes real SQL cursor executions, pool checkout/pre-ping, and DBAPI commit/rollback (not `before_cursor_execute` alone) to prove every current processing path stays within the conservative `consumer_max_db_round_trips_per_attempt=8` cap.
